## v2.20 — 2026-09-04 (하루에 몇 쪽 — 챕터 경계를 존중한 도서 진도 계산)

⚠️ **`BookDetailResponse.detail`/`MaterialsSpecConfirmRequest.details`(book) 호환 깨짐**:
`toc: string[]` → `chapters: {title, endPage}[]`. `MaterialsSpecConfirmResponse.bookPace` 에
`chapters: {title, endPage, sessions}[]` 추가(additive).

### 무엇이 문제였나

목차(`toc`)를 문자열 목록으로만 줬다 — "몇 쪽까지 어떤 챕터"인지, "하루에 몇 쪽 볼지"는
사용자가 직접 셈해야 했다. 게다가 국중 seoji 목차 자체가 best-effort(L0 실측 10권 중
1권)라 대부분의 책은 이 정보가 아예 없었다.

첫 구현(같은 날 이전 커밋)은 `page_count` 균등 분할로만 세션당 쪽수를 냈다 — 목차가
있어도 "챕터별 실제 페이지 체크포인트로 세션을 배정"하지는 않았다. 실측해 보니 41쪽짜리
챕터를 20쪽씩 균등하게 자르면 챕터 중간에서 세션이 끊겼다.

### 이제

**`page_count` 하나만으로 항상 계산되는 진도**가 기본이다 — `spec-confirm` 이 책을 받으면
`goals.deadlines`/`goals.weekly_time`/`goals.frequency` 를 `POST /plans/generate` 와
**같은 함수**(`first_plan_adapter.target_sessions_per_week`)에 태워 시간 예산 기준 세션당
쪽수를 정한다. 목차 유무와 무관하게(L0 10/10) 항상 나온다 — 마감이 없거나 지났을 때만
`bookPace=null`(지어내지 않는다).

**목차 전 챕터에 `endPage` 가 있으면(best-effort, L0 1/10)** 그 시간 예산 기준 쪽수는
목표치로만 쓰고, `_chapter_session_plan` 이 챕터 경계를 존중해 다시 배정한다 — 각 챕터가
`round(챕터 쪽수 ÷ 목표 쪽수)` 세션(최소 1)에 **정확히** 끝나도록, 세션이 챕터 중간에서
안 끊기게. `bookPace.totalSessions` 는 이 챕터별 배정의 합이다(균등 분할 값이 아니다).
목차가 커버하는 마지막 페이지가 `page_count` 보다 작으면(부록·연습문제 등, 흔하다) 그
차이도 "(목차 이후 나머지 분량)" 이름 없는 항목으로 마저 배정한다 — 존재하는 페이지를
없는 셈 치지 않는다. 챕터 중 하나라도 `endPage` 를 모르면(부분 목차) 챕터 배정 자체를
포기하고 균등 분할로 폴백한다.

seoji 원문은 개행 없이 점선(···)+페이지 번호로 항목이 이어붙은 한 덩어리 문자열이라,
챕터 경계마다 **마지막** 페이지 마커만 취하면 실제 페이지 순서와 일치한다(실측 검증).
페이지 번호가 거꾸로 가면(파싱 오류 신호) 그 책 전체의 `endPage` 를 버린다.

계산 값은 **서버가 지금 막 계산한 값만** 슬롯에 싣는다 — 클라이언트가 진도 숫자를 보내도
무시된다(계획 분량에 직접 영향을 주는 산술이라 클라이언트를 신뢰하지 않는다).

라이브 검증(2026-09-04, 실 알라딘+seoji 호출): "Java의 정석 : 기초편"(1000쪽, 15챕터 목차
확보, isbn13 `9788994492049`) + 목표 마감 2026-11-01 · 주 6시간 · 세션 60분 →
균등 분할이었다면 50세션(세션당 20쪽)이었을 것이 **챕터 경계 배정으로 49세션**(챕터 1은
41쪽을 2세션, 챕터 2는 26쪽을 1세션, ... 목차 밖 나머지 300쪽은 15세션)으로 나왔다 —
`materialsNote` 에 "Chapter 1. 자바를 시작하기 전에 (~41쪽까지, 약 2세션)" 형태로 그대로
실려 기존 `materials_for_prompt` 경로를 탄다(새 프롬프트 변수 없음).

## v2.19 — 2026-09-04 (materialMix — 책+영상 병행 확정)

⚠️ **`POST /plans/materials/spec-confirm` 호환 깨짐**: 요청 `detail`(단일) → `details`(배열,
1~2건). 응답 `kind`(단일) → `kinds`(배열). `POST /plans/materials/study-method` 응답에
`materialMix` 추가(additive).

### 무엇이 문제였나

`goals.materials` 슬롯은 자료를 하나만 담았다 — 책을 확정하면 영상이 지워지고 그 반대도
같았다("나중 확정이 이긴다"). 토익처럼 이론(문법서)과 반복 트레이닝(강의)이 둘 다 의미
있는 목표에서, 사용자는 책 아니면 영상 중 하나만 계획에 반영할 수 있었다.

### 이제

`study-method` 가 셋 중 하나를 함께 추천한다 — `"book"`(목차 구조가 뚜렷한 단일 교재로
충분) · `"video"`(설명·시연이 핵심) · `"both"`(이론+트레이닝이 둘 다 필요). 강제하지
않는다 — 사용자가 다르게 골라도 `spec-confirm` 이 받아준다.

`spec-confirm` 은 이제 `details` 배열(책 1개·영상 1개까지, 같은 종류 두 번은 422)을
받아 `goals.materials` 슬롯에 `{"type":"spec","items":[...]}` 로 담는다.
`interview_adapter._materials_note` 가 각 항목을 텍스트로 풀어 이어붙이므로, 두 건을
확정해도 `materials_for_prompt` 의 기존 울타리·경로는 그대로다 — 새 프롬프트 변수도 새
인젝션 방어도 만들지 않았다.

라이브 검증(2026-09-04, 실 Gemini 호출): 토익 900점 목표에 `study-method` 를 물으니
`materialMix="both"` 를 냈다. 해커스 실전 1000제(420쪽, 목차 없음) + 토빡남 재생목록
(32편·1038분)을 같이 확정하고 분해를 돌리니, 세션이 두 소스를 섞어 나왔다 — "해커스 토익
1000제 RC 파트 5 문제 50개 풀기"(책) 다음에 "김진태 토빡남 문법 30모음 영상 시청"(영상)
처럼 이론과 트레이닝이 번갈아 배치됐다.

자세한 설계 근거는 [ADR-0010](decisions/0010-materials-research-pipeline.md).

## v2.18 — 2026-09-03 (spec-confirm 이 계획 생성에 반영된다)

**계약 변경 없음** — `POST /plans/materials/spec-confirm` 의 동작이 바뀐다(v2.09 가 남긴
제약 해소). endpoint·요청/응답 스키마는 그대로다.

### 무엇이 문제였나

v2.09 는 `type="spec"` 을 슬롯에 저장만 했다. `interview_adapter._text_raw` 가
`type=="text"` 만 읽어서, 확정해도 `materialsNote`/`goal_decompose` 는 `(없음)` 그대로였다.

### 이제

`interview_adapter._materials_note` 가 `type=="spec"` 값을 텍스트로 풀어(도서: 페이지
수 + 목차, 영상: 커리큘럼 각 항목의 분량 포함) `materialsNote` 에 싣는다. 그 뒤로는
붙여넣기 텍스트와 **완전히 같은 경로** — `first_plan_adapter.materials_for_prompt` 의
기존 울타리(injection fence) → `goal_decompose`. **새 프롬프트 변수도 새 방어 로직도
만들지 않았다** — 이미 검증된 경로를 재사용한다.

라이브 검증(2026-09-03, 실 Gemini 호출): 3편짜리 영상 커리큘럼(1일차 시제 54분 · 2일차
수동태&수일치 67분 · 3일차 to부정사&동명사 56분)을 확정하고 분해를 돌리면, 세션이 그
순서·주제 그대로 나온다("시제 강의 수강 및 기본 개념 정리" → "수동태&수일치 강의 수강
전반부" → …) — 일반론이 아니라 확정한 자료를 뼈대로 삼는다는 것을 실제 호출로 확인했다.

`spec-confirm` 의 `notice` 도 그에 맞춰 "저장했다" 에서 기존 `/confirm`(③)과 같은
"다음 계획 생성부터 반영된다" 문구로 바뀐다.

자세한 설계 근거는 [ADR-0010](decisions/0010-materials-research-pipeline.md) §5.

## v2.16 — 2026-09-03 (자료 검색 파이프라인 신설 — study-method · catalog)

**`POST /plans/materials/study-method`, `POST /plans/materials/catalog` 신설**(additive,
기존 `materials/search-query`~`materials/confirm` 3단계는 그대로 — 교체 아님).

### 무엇이 문제였나

기존 자료 검색(`materials/search`)은 그라운딩 1회로 **이미 정해진** 자료의 목차를
"확인" 하는 방식인데, 상업 교재는 `RECITATION` 으로 통째로 막힌다(3/4 실패, 인프런 강의는
4/4 통과) — 사용자가 자료를 가장 필요로 하는 부류(토익·수험서)가 정확히 막힌다.

L0 실측([`docs/experiments/l0-materials-source-results.md`](experiments/l0-materials-source-results.md))
이 확인한 사실: 도서 목차는 API 로도 크롤링으로도 안정적으로 못 얻지만(알라딘 0/10, 국중
seoji 1/10·판본별), **영상 강의는 재생목록 검색으로 커리큘럼(영상 제목)+분량(재생시간)이
통째로 온다(4/4)**. 자세한 설계 근거는 [ADR-0010](decisions/0010-materials-research-pipeline.md).

### 이제

    POST /plans/materials/study-method   목표 → 추천 방식 + 도서/영상 검색어 2종
                                          (LLM 구조화 호출 1회, 그라운딩 아님)
    POST /plans/materials/catalog        확인된 검색어 → 알라딘/YouTube 후보 검색
                                          (LLM 0회, API 만)

- `study-method` 는 아직 아무것도 검색하지 않는다 — 검색어를 사용자가 확인·편집한 뒤에야
  `catalog` 가 실제로 나간다(①의 프라이버시 원칙과 동일).
- `catalog` 의 두 소스는 독립적으로 실패한다 — 한쪽이 안 되도 다른 쪽 후보는 그대로 온다.
- 후보에는 목차·분량이 아직 없다 — 후보를 고른 뒤 그 한 건만 상세 조회하는 단계는 아직
  배선하지 않았다(ADR-0010 §4·§5, 후속).
- ⚠️ YouTube `search.list` 는 1회 100유닛/일일쿼터 10,000유닛 — **앱 전체 하루 ~100회가
  상한**이고 사용자별 상한은 아직 없다. 초과하면 `videos=[]` + `videoNotice` 로 알릴 뿐
  500 이 아니다.
## v2.15 — 2026-09-02 (캘린더 일정이 계획에 반영된다 — freebusy busy 소스 배선, ADR-0009 D4)

**동작 변경 — `POST /plans/generate` · `GET /calendar/freebusy`.** 응답 스키마 변경 없음.
`generate` 의 `warnings` 에 항목이 하나 늘 수 있다.

### 무엇이 바뀌었나

v2.05 는 **연결까지**였다. 토큰은 저장했지만 그 캘린더를 아무도 읽지 않아 계획은 여전히
남의 일정 위에 잡혔다. 이제 계획 생성이 캘린더를 읽어 **다섯 번째 busy 소스**로 넣는다:

```
time_policies(수면·점심) + fixed_schedules(수업) + existing_busy(승인된 내 카드)
+ calendar(구글 일정) + past
```

지평 전체를 **한 번에** 조회한다 — `busy_for_day` 안에서 부르면 날짜마다 API 왕복이 난다.
`existing_busy` 와 같은 모양(날짜별 dict)이라 스케줄러 쪽 변경이 없다.

⚠️ **두 배치 뷰 모두에 넣는다.** 1차 배치는 `roomy_busy_for_day`, 2차는 `busy_for_day` 라는
서로 다른 뷰를 쓴다. 한쪽에만 넣으면 하루가 빡빡해지는 순간(=2차가 도는 순간) 캘린더 일정
위에 카드가 잡힌다 — `pad_busy` 가 정확히 그 함정에 빠져 있다(ADR-0009 D4 ①이 경고한 것).
테스트가 **두 뷰 각각을 빼면 빨간불이 되는지**까지 확인한다.

캘린더 일정에는 **여백을 덧대지 않는다** — 고정일정(수업)과 같은 취급이다. 그건 '쉴 수 없는
시간'이지 집중 작업이 아니고, 여백을 주면 일정 직후가 통째로 날아간다(v1.97 결정).

### 실패는 계획을 죽이지 않는다

연결이 없거나·토큰이 죽었거나·Google 이 느리면 캘린더 없이 예전처럼 진행한다.

다만 **연결해 둔 사용자에게 조용히 실패하면 안 된다** — "연결했는데 수업 위에 계획이 잡혔다"
는 사용자가 스스로 알아챌 수 없다. 그래서 세 경우를 가른다:

| 상태 | 계획 | 사용자에게 |
| --- | --- | --- |
| 연결 안 함 (대다수) | 캘린더 없이 진행 | **아무 말 없음** — 매번 권유하면 알림 피로 |
| 정상 | 반영 | — |
| 연결됨 + 못 읽음 | 캘린더 없이 진행 | `warnings` 한 줄 |

토큰 갱신이 `invalid_grant` 로 실패하면 사용자가 Google 에서 권한을 뺏은 것이라 `revoked_at`
을 찍어 재연결을 안내한다. **일시적 실패(네트워크·5xx)는 연결을 끊지 않는다** — 그 구분이
`OAuthError.retryable` 이다.

### `GET /calendar/freebusy` 가 실제 조회가 된다

예전엔 고정 데모 구간을 돌려주는 mock 이었다. 이제 실제 캘린더를 읽고, **연결이 없으면
404 `CALENDAR_NOT_CONNECTED`** 다 — 빈 목록으로 주면 "일정 없음" 과 구분되지 않아 FE 가
"캘린더가 되고 있다" 고 믿는다. `from`/`to` 는 KST 날짜, 최대 60일.

### 아직 아닌 것

**겹치기 회피까지다.** ADR-0009 D4 의 나머지 두 룰은 아직이다 —
① **전이 버퍼**(외부 일정 앞뒤 이동 시간), ② **부하 감쇠**(직전 연속 일정이 길수록 그 뒤
슬롯의 허용 카드 길이를 낮춘다 — 4시간 시험 직후에 3시간 딥워크를 넣지 않는다).
그래서 지금은 **일정 끝나자마자 0분 간격으로 카드가 붙을 수 있다.**

일정의 **제목·장소는 읽지 않는다**(freebusy 스코프). 앞뒤 일정의 '내용'을 보는 판단은 이
설계로는 불가능하고, 길이·인접성으로 근사하는 것이 ①② 의 몫이다.

## v2.14 — 2026-09-02 (Google Calendar 연결 실구현 — OAuth 보류 해제, 읽기 전용)

**신규 동작 — `/calendar/connect` (POST/DELETE).** 응답 스키마는 기존 정의 그대로
(`CalendarConnection`). 마이그레이션 없음 — `calendar_connections` 테이블은 이미 있었다.

### 무엇이 바뀌었나

Issue #17 Alpha MVP 결정이 **Google Calendar OAuth 자체를 P1 로 미뤄** 두 엔드포인트가
501 이었다. ADR-0009 D4 가 그 보류 해제를 제안했고(계획 단위가 분으로 바뀌면서 "외부 일정
앞뒤"를 모르는 스케줄러가 못 지킬 계획을 만든다), 팀 합의로 해제한다.

### 범위 — 읽기 전용, 스코프 하나

스코프는 `https://www.googleapis.com/auth/calendar.freebusy` **하나**다. 스케줄러의 세 룰
(전이 버퍼·부하 감쇠·자투리)에 필요한 건 **구간의 길이와 인접성뿐**이고 제목·장소는 필요
없다. `calendar.readonly` 로 넓히면 남의 일정 제목이 우리 DB 근처로 오는데 그만한 값이 없다
— 테스트가 스코프 문자열을 고정한다.

`events.insert`(write-back)는 **P1 유지**. `sync-preview`/`approve-insert` 는 여전히 stub 이고,
freebusy 조회를 스케줄러에 배선하는 것도 후속이다. 이 버전은 **연결까지**다.

### 동작

- `POST /calendar/connect` — authorization code → 토큰 교환 → `*_encrypted` 저장.
  **멱등**: 재연결은 새 행이 아니라 기존 행 갱신(`user_id` 유니크 + soft delete 라 새 INSERT
  는 제약에 걸린다). 실패는 422 `COMMON_VALIDATION_ERROR` — 새 에러 코드를 만들지 않았다.
- `DELETE /calendar/connect` — **204, 멱등**. 연결이 없어도 204 다(두 번 눌렀다고 404 를 주면
  "이미 끊긴 상태"가 실패로 보인다). `revoked_at` soft delete 를 **먼저 커밋**하고 Google 쪽
  권한 회수는 그 뒤에 best-effort — 순서를 뒤집으면 Google 은 끊겼는데 우리는 연결됐다고
  믿는 상태가 생기고, 회수 실패로 예외를 올리면 사용자가 연결을 **해제조차 못 하게** 된다.

⚠️ **refresh token 은 최초 동의 때만 온다.** 갱신 응답에 없는 게 정상이라, 저장 계층이
None 을 만나면 **기존 값을 유지**한다. 그대로 덮어쓰면 다음 갱신이 불가능해져 연결이
하루 뒤에 조용히 죽는다. 같은 이유로 최초 연결에 refresh token 이 없으면(동의 URL 에
`access_type=offline` 이 빠진 경우) 연결 자체를 실패로 본다 — 반쯤 된 연결을 저장하지 않는다.

### 기능 스위치 — 기본 OFF

`GOOGLE_CALENDAR_ENABLED=false`(기본)이거나 `GOOGLE_OAUTH_CLIENT_ID`/`_SECRET` 이 비어 있으면
두 엔드포인트는 **예전처럼 501**. Cloud 콘솔 셋업(client_secret · 승인된 리디렉션 URI)은
사람 손이 필요해서, 준비 전에 배포돼도 사용자가 깨진 동의 화면을 만나지 않게 하는 안전핀이다.

### 새 의존성 없음

`google-api-python-client` 는 동기이고 무겁다(discovery 캐싱·httplib2). 필요한 건 토큰
엔드포인트 POST 하나뿐이라, 레포에 이미 있는 `requests` 를 `web_fetch`·`web_push` 와 같은
방식으로 감쌌다 — `to_thread` + 이중 timeout. `uv add` 가 없다.

**동작 변경 — `POST /plans/generate`.** 응답 스키마 변경 없음. 잘못된 '대기 단계' 고지가
`warnings` 에서 사라지고, 빠져 있던 세션이 계획에 들어온다.

### 무엇이 잘못됐었나

'외부 대기' 단계를 세션에서 걷어내는 결정적 백스톱(#225)이 `대기` 를 **부분 문자열**로
찾고 있었다. 한국어에서 '대기' 를 품은 낱말은 흔하다:

| 제목 | 예전 | 지금 |
| --- | --- | --- |
| 대학 생활 및 인턴십 주요 활동 **연대기** 타임라인 작성 | 세션에서 제외 | 유지 |
| **대기업** 자기소개서 초안 작성 | 세션에서 제외 | 유지 |
| **대기오염** 관련 논문 읽기 | 세션에서 제외 | 유지 |
| 장학금 심사 결과 **대기** | 제외 | 제외 (그대로) |

라이브 실측(2026-08-29 공채 준비 시나리오)에서 첫 줄이 실제로 났다. 노드는 트리에 남고
세션만 없어져 사용자에겐 "이 단계만 일정이 없다" 로 보였고, 고지 문구는 "**상대의 처리를
기다리는 단계라** 오늘 할 일로 만들지 않았어요" 라는 사실과 다른 말이었다. 취준 도메인은
'대기업' 이 흔해 재발률이 높다.

### 지금

`대기` 는 **낱말일 때만** 잡는다 — 앞이 한글이 아니고, 뒤가 한글이 아니거나(공백·끝·문장
부호) '대기' 에 직접 붙는 어미·조사(`중·하·상태·가·를…`)일 때. `기다리` 는 그대로다.

붙여 쓴 '발표대기' 는 이제 안 걸린다(미탐). 의도한 트레이드오프다 — 이 백스톱의 원칙이
"오탐이 미탐보다 나쁘다" 이고, 넓은 판별은 분해 프롬프트 규칙이 맡는다.

## v2.07 — 2026-09-01 (축 주기 시드가 온보딩 프로필로도 열린다)

**`POST /plans/mandala/next-cycle` 응답에 `seedSource` 추가**(additive). 422 조건 완화.

### 무엇이 문제였나

v2.06 은 계획 인터뷰가 없으면 무조건 422 였다. "가용 시간을 지어내지 않는다" 는 원칙은 맞지만
**조건이 틀렸다** — 활동 시간대는 인터뷰에만 있는 게 아니다. `persist_profile_from_outcome` 이
인터뷰 답을 `behavioral_profiles.preferred_start_time`/`preferred_end_time` 에 저장하고, 설정
화면(`PATCH /settings/...`)이 그걸 편집한다. **프로필이 그 값의 최신 진실**이다.

그래서 온보딩·설정에서 활동 시간대를 직접 넣은 사용자가, 계획 인터뷰를 안 했다는 이유만으로
자기 만다라 축을 못 열었다. 만다라트만 하고 들어온 사용자가 정확히 이 경우다.

### 이제

시드를 **인터뷰 → 프로필** 순으로 찾는다.

| 순서 | 출처 | `seedSource` |
| --- | --- | --- |
| ① | 최근 '정상 종료' 계획 인터뷰 outcome | `"interview"` |
| ② | `behavioral_profiles`(활동 시간대·피크·집중 길이) + `interaction_styles.recovery_tone` + `users.focus_mode_preferences` | `"profile"` |
| ③ | 활동 시간대를 어디서도 모름 | 422 |

- ①이 언제나 우선이다 — 프로필은 인터뷰 답의 **파생**이라 원본이 있으면 원본을 쓴다(프로필엔
  목표별 슬롯인 주당 시간·세션 길이가 없어 정보가 준다).
- ②는 `profile_memory.seed_slots_from_profile`(재인터뷰 시드)에 **활동창만 더해** 기존
  `interview_adapter.build_outcome` 에 넣는다. 새 기본값을 만들지 않았다 — 못 채운 슬롯은
  그 함수의 문서화된 기본값으로 가고 그 키가 `unresolvedSlots` 에 남는다.
  그쪽이 활동창을 안 만드는 이유(결과가 `interview_slot_answers` 에 UPSERT 돼 옵션에 없는
  표기가 '사용자의 답'으로 남는 사고, v2.01)는 여기 해당하지 않는다 — 이 슬롯 맵은 계획 한 번을
  위한 임시 값이고 저장되지 않는다.
- ②로 만든 계획은 `warnings` 에 "계획 인터뷰 대신 저장된 활동 시간대로 배치했어요" 가 실린다.
  무엇으로 배치했는지 모르게 두지 않는다.
- ③의 기준은 **활동 시간대 하나**다. 피크·집중 길이는 없으면 기본값으로 굴러가지만, 활동창은
  "언제 배치해도 되는가" 라 모르면 배치가 통째로 추측이 된다. 프로필 행은 있는데
  `preferred_start_time`/`preferred_end_time` 이 비어 있는 경우도 여기에 포함된다.

### 호환

- ⚠️ **422 가 200 으로 바뀌는 경우가 있다** — 프로필에 활동 시간대가 있는 사용자. 넓히는
  방향이라 기존 성공 호출의 동작은 무변경(`seedSource="interview"`).
- 안내 문구가 바뀌었다: "계획 인터뷰를 먼저 진행해 주세요" → "활동 시간대를 아직 몰라요.
  계획 인터뷰를 진행하거나 설정에서 활동 시간대를 정해 주세요." (에러 코드는 그대로
  `COMMON_VALIDATION_ERROR`).
- 마이그레이션 없음. LLM 비용 영향 없음(프로필 → 슬롯은 순수 함수).

## v2.06 — 2026-09-01 (축 → 다음 2주 계획 — 만다라트가 실행으로 이어진다)

**추가 endpoint 1개** `POST /plans/mandala/next-cycle`. 기존 필드·경로 무변경.

### 무엇이 문제였나

v2.05 로 만다라트를 안전하게 다시 세울 수 있게 됐지만, **다시 세운 다음에 할 게 없었다.**

`POST /plans/generate` 의 시드는 계획 인터뷰 outcome 이고 그 안의 `is_heaviest` 는 **인터뷰
당시** 사용자가 고른 목표다. 만다라트를 다시 세워 축이 통째로 바뀌어도 계획은 여전히 옛
목표를 분해한다. 축 제목이 `goals.heaviest` **보기**로 들어가는 배선(ADR-0008 §8 "B")은
있지만 그건 *새 인터뷰를 다시 할 때* 얘기고, 축 하나 열자고 딥 인터뷰를 다시 하라는 건
현실적인 요구가 아니다.

결과적으로 사용자 입장에서 만다라트는 그리고 나면 끝나는 그림이었다 — ADR-0008 이 "만들고
나면 죽은 문서가 되는" 걸 막겠다고 한 바로 그 상태다.

### 이제

`POST /plans/mandala/next-cycle` 한 번으로 **승격 → 시드 교체 → 계획 Draft** 까지 간다.

1. **승격(멱등)** — 이미 승격된 축이면 그 목표를 그대로 쓴다(`goalTier` 무시, 기존 tier 유지).
   새로 승격할 때만 Focus≤3/Maintain≤5 를 잰다. 같은 축을 두 번 열어도 목표가 안 쌓인다.
2. **시드 교체** — 최근 계획 인터뷰 outcome 의 `coreGoals` 만 이 축으로 갈아끼운다. 정체성·
   활동 시간대·선호는 사용자가 실제로 답한 값 그대로다. 같은 제목의 목표를 인터뷰에서 이미
   답했으면 주당 시간·세션 길이·케이던스도 살린다.
   ⚠️ **계획 인터뷰가 없으면 422** — 가용 시간을 지어내지 않는다(v2.01 과 같은 원칙).
3. **칸이 계획 뼈대가 된다** — 그 축의 칸들이 그대로 마일스톤이 된다(완료한 칸 제외, 순서
   유지). 이게 핵심이다: 안 그러면 분해가 축 제목만 보고 뼈대를 다시 지어내고, 사용자가
   만다라트에서 확정한 분해를 계획이 무시한다. `useCellsAsMilestones=false` 로 끌 수 있다.
4. **이후는 `/plans/generate` 와 같은 경로** — 분해·배치·Draft 저장이 한 함수(`_run_first_plan`)로
   모였다. 두 입구가 서로 다른 계획을 만들면 안 된다.

**지평이 2주인 이유**는 여기에 규칙을 새로 넣어서가 아니다. 시드의 heaviest 제목이 승격된
목표 제목과 같으므로 기존 `_max_plan_weeks`(ADR-0008 §3) 판정이 그대로 걸린다. 만다라 계획의
'2주'가 두 곳에서 따로 정의되지 않게 하려는 것이다.

응답은 `FirstPlanResponse` + `axis`(`{ nodeId, orderIndex, title, goalId, goalTier,
newlyPromoted }`).

### 호환

- ⚠️ **자동 적용이 아니다**(§1.4). `isDraft=true` 이고 카드·블록은 기존
  `POST /plans/{planId}/approve` 를 눌러야 생긴다. 만다라 전용 승인 경로를 만들지 않은 이유는
  HITL 게이트를 두 벌로 만들지 않기 위해서다 — FE 의 계획 미리보기 화면도 그대로 재사용된다.
- 마이그레이션 없음. 새 컬럼·인덱스 0개.
- LLM 비용: `/plans/generate` 와 동일(분해 1콜). 별도 증가 없음. `planning` 모듈 호출 상한을
  그대로 탄다.
- `POST /plans/generate` 는 동작·응답 무변경 — 본체만 `_run_first_plan` 으로 빠졌다.

## v2.05 — 2026-09-01 (만다라트 "다시 세우기" — 사전 확인 + 승계)

**추가 endpoint 1개 + `approve` 응답에 `carriedOver` 절**(additive, 기존 필드 무변경).

### 무엇이 문제였나

목표 화면의 **[다시 세우기]** 는 새 endpoint 가 필요 없었다 — `POST /plans/mandala/subgoals`
→ `generate` → `approve` 를 한 번 더 타면 `persist_mandala` 가 옛 트리를 보관하고 새 73행을
쓴다. 여기까지는 설계대로다.

문제는 **보관되는 것에 사용자가 손으로 쌓은 것이 매달려 있다**는 점이다. 셋 다 archived 노드를
가리킨 채 화면에서만 사라졌다:

| 무엇 | 어디에 | 다시 세운 뒤 |
| --- | --- | --- |
| 칸 완료 표시 | `goal_nodes.completed_at` | 전부 0으로 |
| 축 승격 | `goal_nodes.promoted_goal_id` | 목표는 남지만 축 배지·`goals.heaviest` 보기·2주 주기 스코프에서 빠짐 (셋 다 `archived_at IS NULL` 을 건다) |
| 반복형 칸 | `habits.goal_node_id` | 습관은 계속 주간 instance 를 만드는데 그 칸이 만다라 뷰·주간 리포트에 없음 |

그리고 버튼을 누르기 전에 **무엇이 사라지는지 알 방법이 없었다.** AI 산출은 Draft + 3버튼으로
막아 두었는데(§1.4), 정작 73칸을 통째로 갈아엎는 이 동작에는 미리보기가 없었다.

### 이제

**① 승인 전 — `GET /goals/{goalId}/mandala/rebuild-preflight`** (읽기 전용, LLM 0콜, DB 쓰기 0)

지금 트리에 걸려 있는 것을 그대로 돌려준다 — `totalCells`/`completedCells`,
`promotedAxes[]`(축 + 그 축에서 승격된 목표), `linkedHabits[]`(반복형 칸 + 습관),
`liveActionItems`, 그리고 확인 시트에 그대로 얹을 `warnings[]`(서버가 완성한 문장,
`/plans/generate` 의 `warnings` 와 같은 규약). 아직 트리가 없으면 `hasTree=false` + 전부
0/빈 배열 — 404 가 아니라 "정상, 그냥 비어 있음"(`GET /goals/{id}/mandala` 와 같은 규약)이라
처음 세우는 경우도 FE 가 같은 경로를 타고 확인 시트만 건너뛴다.

**② 승인 때 — 제목이 같은 자리로 승계**

`persist_mandala` 가 옛 트리를 보관하기 **전에** 읽어 두고, 새 노드를 flush 한 **뒤에**
이어붙인다(순서가 계약이다 — `habits.goal_node_id` UPDATE 가 새 leaf INSERT 보다 먼저 나가면
FK 가 깨진다). 키는 축이 `title`, 칸이 `(축 title, 칸 title)` — 칸 제목만으로 맞추면
"매일 30분" 같은 흔한 칸이 엉뚱한 축으로 건너뛴다.

- 이어지는 것: 칸 `completedAt`, 축 `promotedGoalId`, 반복형 칸의 습관 링크.
- **AI 가 채운 제목·이유는 안 이어진다** — 다시 세우기의 목적 자체가 그것이다.
- 자리를 못 찾은 쪽은 **지우지 않는다**: 승격된 목표는 그대로 남고(축 배지만 빠짐), 습관은
  `goalNodeId=null` 로 링크만 풀려 단독 습관이 된다(주간 횟수 기록 보존). hard delete 없음.

`POST /plans/mandala/{planId}/approve` 응답에 `carriedOver` 가 붙는다 —
`{ completedCells, promotedAxes, linkedHabits, droppedPromotedAxes[], droppedLinkedHabits[] }`.
앞 셋은 이어진 개수, 뒤 둘은 끊긴 것의 **이름**이라 FE 가 승인 직후 그대로 보여줄 수 있다.
조용히 사라지는 게 이 기능의 유일한 위험이라 개수가 아니라 이름으로 돌려준다.
처음 세우는 경우엔 전부 0/빈 배열이고, 멱등 재승인은 승인 시점 스냅샷을 그대로 재현한다.

### 호환

- 기존 필드 무변경. `carriedOver` 는 추가 필드이고 처음 세우기에서는 0/빈 배열이라 FE 가
  안 읽어도 종전과 같다.
- 마이그레이션 없음 — 새 컬럼·인덱스 0개. 승계는 기존 컬럼을 새 행으로 옮겨 쓸 뿐이다.
- LLM 비용 영향 없음 — preflight 는 0콜, 승계는 `approve`(원래 0콜) 안에서 끝난다.

## v2.04 — 2026-08-29 (카드 [시작]이 계획 교체와 겹칠 때 유령 카드가 안 생긴다, #368)

**동작 변경 — `POST /today/actions/{actionId}/start` 의 경합 처리.** 스키마 변경 없음.

### 무엇이 문제였나

`supersede_previous_plan`(계획 승인·목표 완료가 이전 카드를 보관하는 함수)의 독스트링은
"카드 SELECT 는 FOR UPDATE — 동시에 [시작]하는 요청과 교차해 '보관됐는데 실행 중'인 유령
카드가 생기지 않게 직렬화한다" 고 약속했다. **한쪽만 잠그면 직렬화가 아니다.**

`today.start_action` 은 락 없는 SELECT(`get_by_id`)로 읽고 상태 전이를 ORM 에 맡겼다.
SQLAlchemy 가 내는 `UPDATE ... WHERE id = :id` 에는 `archived_at` 술어가 없어, READ
COMMITTED 에서 교체 트랜잭션의 락이 풀린 뒤 **보관된 행에 그대로 적용**됐다. 실 Postgres
커넥션 두 개로 재현된다:

```
수정 전: T2 읽기 찾음 → UPDATE 커밋 → status='in_progress' archived=True   (유령)
수정 후: T2 읽기 없음(락 대기 1.06s) → 404               → status='planned'  archived=True
```

유령 카드는 `list_pending_reflection` 이 `execution_events` 만 보고 `action_items` 에
join 하지 않으므로 **회고 화면까지 새어 나갔다.**

### 이제

`start_action` 이 카드를 `ActionItemRepo.get_by_id_for_update`(= `FOR UPDATE` +
`archived_at IS NULL`)로 읽는다. 교체가 진행 중이면 락을 기다렸다가 갱신된 행으로 WHERE 를
다시 평가하고, 그 사이 보관됐으면 행이 빠져 **404** 로 끝난다.

- 사용자에게 보이는 변화: 계획 교체와 정확히 겹친 [시작] 요청이 201 대신 **404** 를 받는다.
  이미 사라진 카드이므로 FE 는 기존 404 처리(목록 새로고침)로 충분하다.
- 노출 창은 좁다 — 계획 승인·목표 완료가 도는 중에 사용자가 정확히 그 카드를 눌러야 한다.

⚠️ **상태만 조건부로 막는 방법(`UPDATE ... WHERE archived_at IS NULL`)은 택하지 않았다.**
그 방식은 `status` 는 지키지만 그 전에 만들어진 `execution_events`·`scheduled_block` 이
남아, 정작 문제였던 **회고 화면 누출을 못 막는다.** 읽기 시점에 잠가야 아무것도 만들기 전에
끝난다. (같은 행을 조건부로 UPDATE 해도 결국 같은 락을 기다리므로 지연 이점도 없다.)

### 범위 밖 — 함께 관측했지만 안 고친 것

`today.quick_check_in` 도 같은 모양(`get_by_id` → `action.status = ...`)이다. 다만 피해가
다르다: 체크인은 이미 존재하는 실행을 매듭짓는 것이라 새 행을 만들지 않고, 보관된 카드에
최종 상태가 찍히는 데 그친다(회고 누출 없음). 별도로 판단할 일이라 이 PR 에 묶지 않았다.

## v2.03 — 2026-08-28 (호출 상한이 LLM 호출이 아니라 **요청**을 센다 — 온보딩 차단 해제, #370)

**동작 변경 — 사용자별 일일 상한의 계수 단위.** 응답 스키마 변경 없음.
모든 응답에 `X-Request-ID` 헤더가 추가된다(신규, 읽기 전용).

### 무엇이 문제였나

`LLM_ENDPOINT_DAILY_CALL_LIMIT` 가드는 "이 엔드포인트를 오늘 몇 번 실행했는가"를 센다고
주석과 독스트링 양쪽에 적어 놨지만, 실제로는 `llm_runs` **행 수**를 셌다. 행은 **LLM 호출
1회당** 1개이고 엔드포인트 1회는 호출을 여러 번 한다:

| 엔드포인트 1회 | llm_runs 행 |
| --- | --- |
| `POST /interview/.../answers` (칩 답) | 2 — ambiguity + next_question |
| `POST /interview/.../answers` (자유서술) | 3 — + slot_extraction |
| `POST /plans/generate` | 최대 7 — 분해×3 + 검토×3 + 마일스톤 (`MAX_REPLAN=2`) |

그래서 상한 20 은 "20회 실행"이 아니라 **인터뷰 8턴**이었다. 계획 인터뷰는 필수 슬롯이
18개라 완주에 요청 19건 이상 · LLM 49콜이 든다 — **신규 사용자가 온보딩을 끝낼 수 없었고**,
재인터뷰도 같은 이유로 막혔다. 배포 환경에서 7번째 답변부터 429 가 났다.

상한을 올리는 건 증상 처치다. 이 결합에서는 **LLM 노드를 하나 붙일 때마다 상한이 조용히
조여진다** — 실제로 `harvest_slots` 가 추가되며 턴당 2콜이 3콜이 된 게 이번 사고의 경로다.

### 이제

`observability/correlation` 미들웨어가 요청마다 `trace_id` 를 심고, 그 요청 안의 모든 LLM
호출이 같은 값을 단다(ContextVar — 호출부를 하나씩 고치지 않아 **앞으로 생길 호출부도
자동으로 덮인다**). 가드는 `COUNT(DISTINCT trace_id)` 로 **요청**을 센다.

- 호출자가 LLM 을 몇 번 부르든 상한이 조여지지 않는다.
- trace_id 가 NULL 인 행(cron·스크립트, 그리고 이 변경 이전 행)은 **각각 1회**로 센다.
  `COUNT(DISTINCT)` 가 NULL 을 무시하게 두면 그 경로에서 **가드가 조용히 꺼진다** —
  틀리더라도 예전처럼 빡빡한 쪽으로 틀린다.

⚠️ **`X-Request-ID` 요청 헤더는 무시한다.** trace_id 가 상한의 계수 키가 된 이상 클라이언트가
값을 고를 수 있으면 매 요청에 같은 값을 보내 하루치를 1회로 접을 수 있다. 서버 생성 값만
쓰고, 응답 헤더로만 돌려준다.

### 인터뷰는 별도 상한 — 단위만 고쳐서는 안 풀렸다

단위를 고쳐도 **완주 요청 19~21건 vs 상한 20** 이라 재질문이 한 번만 있어도 여전히 막혔다.
20 은 "하루에 인터뷰 턴을 20번 넘게 부를 일은 없다"는 전제로 고른 값인데, 인터뷰 **한 번**이
20턴짜리 흐름이라 전제부터 틀렸다.

- `LLM_ENDPOINT_DAILY_CALL_LIMIT_INTERVIEW` 신설, 기본 **60**.
  완주 1회(~21) + 재질문 여유 + 같은 날 재인터뷰(~14) 를 합쳐도 40 안쪽이다.
- 나머지 모듈(계획·만다라트·회복)은 base **20** 유지 — 이제 진짜 "20회 실행"이다.
- base 가 0(무제한)이면 인터뷰 오버라이드도 함께 꺼진다. 운영 스위치가 반만 꺼지면 안 된다.

### 왜 안 잡혔나

기존 테스트 9개는 가드를 **합성 `llm_runs` 행**으로만 검증했다 — 실제 호출자가 한 번에 몇
행을 남기는지 보는 테스트가 없어서, 가드는 자기 가정에 대해서만 초록불이었다.
`tests/test_endpoint_invocation_counting.py` 가 인터뷰를 끝까지 몰아 **완주 요청 수 ≤ 상한**을
못 박는다. 슬롯을 늘리거나 상한을 낮추면 여기서 먼저 깨진다.

`env-check.yml` 도 예산·상한 값을 리포트하지 않아 prod 드리프트가 안 보였다 — 이제 찍는다.

칩 답이 **슬롯이 실제로 제시한 보기(options)로 검증되지 않았다.** harvest LLM 의

프로필 시드는 `f"{n}분"` 을 만들어 넣었다. 그래서 슬롯에 없는 문자열이 **사용자의 답으로**
저장돼 왔다.

이 구멍으로 사고가 두 번 났다. 둘 다 파서가 예상 못 한 문자열을 만나 숫자를 잘못 읽은 것이다:

| | 값 | 결과 |
| --- | --- | --- |
| v2.00 | `"2시간 이상"` | **2분** — 세션 길이 상한이 2분이 돼 계획 전체가 붕괴 |

| v2.01 | 프로필 시드 `"2분"`/`"120분"` | 옵션에 없는 표기가 사용자의 답으로 남아 백필을 틀리게 할 뻔함 |

파서를 하나씩 고치는 건 두더지잡기다. **저장 경계에서 어휘를 좁히면** 그 부류가 통째로 닫힌다.

### 이제

`interview_catalog.canonical_chip` 이 단일 관문이다. 세 단계로 옵션에 맞춘다:

1. 정확 일치
2. **공백 무시** 일치 — LLM 이 `"2시간이상"` 처럼 붙여 쓰는 경우
3. **시간 값 일치** — `"120분"` → `"2시간 이상"`. 표기가 달라도 같은 시간이면 옵션 표기로

정책은 출처에 따라 갈린다:

- **harvest LLM · 프로필 시드 → 못 맞추면 버린다.** 슬롯이 열린 채 남아 인터뷰가 **실제
  보기를 들고 다시 묻는다.** 추측한 값으로 슬롯을 닫는 것보다 한 번 더 묻는 편이 낫다.
- **사용자가 방금 누른 답 → 표기만 정규화하고 거부하지 않는다.** 거기서 값을 버리면 "칩을
  눌렀는데 서버가 미응답으로 보고 같은 질문을 또 하는" 루프가 된다. 카탈로그 옵션은 시간이
  지나며 바뀌므로(주당 시간 척도가 한 번 개편됐다) 옛 척도를 든 클라이언트를 그 루프에
  빠뜨릴 수 없다.

⚠️ **이미 저장된 답은 재검증하지 않는다.** 지난 인터뷰에서 이어받는 값(`_carry_over_slots`)
은 사용자가 실제로 고른 답이고, 옛 척도 옵션(`"6시간"` 등)을 담고 있을 수 있다. 저장 시점에
막는 것과 저장된 것을 지우는 것은 다른 일이다.

### 부수 효과 — 시드가 옵션 표기로 정규화된다

`profile_memory.seed_slots_from_profile` 이 이제 `attention_span=120` 을 `"2시간 이상"` 으로
시드한다(예전엔 `"120분"`). 옵션에 못 맞추는 값(설정에서 45분으로 바꾼 경우 등)은 **아예
시드하지 않는다** — 그 슬롯은 열린 채 남아 실제 보기로 묻는다. 재질문이 한 번 늘지만,
사용자가 고른 적 없는 값이 답으로 저장되는 것보다 낫다.

폴백이라, `goals.session_length` 를 답하지 않은 사용자에게는 **세션 길이 상한이자 주당
분량의 기준**이 된다.

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| `focus_duration_min` | **2** | 120 |
| 세션 길이 상한 | **2분** | 120분 |
| 주당 분량 | **30분** | 360분 |
| 정규화(15·45·120분 카드) | **[10, 10, 10]** | [15, 45, 120] |

파서 버그 자체는 예전부터 있었지만 **잠복 상태**였다 — v1.96 이전에는
`normalize_action_minutes` 가 이 경로에서 통째로 no-op 이라 그 값이 아무 데도 안 쓰였다.
v1.96 이 "미답 경로의 무검증 구멍" 을 메우면서 오염된 값을 상한으로 승격시켰다.

수정: 시간 단위를 읽는 파서(`_chip_duration_min`)로 교체 — `goals.session_length` 는
처음부터 이걸 쓰고 있었다. 같은 파서를 쓰던 `recovery.downscope_unit`("5분"~"30분")도
값이 바뀌지 않는다. 더해서 **`session_min_for` 에 15분 하한**을 두어, 상한이 실행 불가능한
값이 되는 경로를 한 번 더 막았다. `normalize_action_minutes` 의 하한도 상한을 넘지 않도록
묶었다(넘으면 클램프가 상한을 조용히 무시한다).

### ② 【중】 재계획 하루 상한이 최장 **카드** 로 부풀었다

v1.97 은 "상한 ≥ 최장 **세션**" 만 보장하면 된다고 적었는데, 코드는 후보 **카드** 길이로
올렸다. 스케줄러의 배치 단위는 `focus_chunk_min` 으로 쪼갠 세션이라, 쪼개질 카드 때문에
상한만 올라가고 실제 세션은 그보다 짧다. 실측(폴백 튜닝 chunk=60 / cap=180): 60분 후보
6개면 하루 120분씩인데 240분 후보 하나를 더하자 어떤 날이 **240분**이 됐다.
수정: `min(카드, focus_chunk_min)` 의 최댓값으로 잰다.

### 함께 정리한 것

- `test_days_needed_formula_is_unchanged_by_the_minute_unit` 이 **공허했다** — 두 산식을
  테스트 안에서 계산해 비교할 뿐 프로덕션 코드를 호출하지 않아, 그 줄을 어떻게 바꿔도
  통과했다. 산식을 `first_plan_adapter.placement_days_needed` 로 꺼내 실제 함수를
  호출하는 테스트로 바꿨다.
- 두 수정 모두 **뮤테이션 검사**로 확인했다 — 픽스를 되돌리면 새 테스트가 실패한다.

## v1.99 — 2026-08-28 (주간 리뷰에 분 가중 요약 추가 — ADR-0009 D5)

**필드 추가 — `GET /reviews/weekly`, `POST /reviews/weekly/generate`.** 기존 필드는 전부
불변이라 **기존 클라이언트는 안 깨진다**. DB 마이그레이션 없음.

### 무엇이 문제였나

`adherenceRate` 를 비롯한 주간 KPI 가 전부 실행 **건수** 비율이다. 계획 세션이 전부 비슷한
길이일 때는 건수가 곧 시간이었지만, 길이가 작업 내용을 따라가면(v1.96) 둘이 갈라진다.

> 이번 주에 15분짜리 잡무 9개를 다 하고, 3시간짜리 자소서 1개를 못 했다.
> → `adherenceRate` **0.9**. 실제로 한 건 135분, 못 한 건 180분 — **계획의 43%**.

주간 리포트가 "잘하고 있어요" 라고 말하는데, 사용자는 정작 이번 주에 제일 중요한 걸 못 한
상태다. 게다가 **"예상 대비 실제" 를 볼 수단이 아예 없었다** — `actualDurationMinutes` 는
벽시계일 뿐 계획 길이와 한 번도 비교되지 않는다.

### 이제

```json
"effort": {
  "plannedMinutes": 315,
  "completedMinutes": 135,
  "actualMinutes": 140,
  "adherenceRate": 0.4286
}
```

- ⚠️ **기존 `adherenceRate` 정의는 바꾸지 않는다.** 바꾸면 과거 주차와 비교할 수 없다.
  분 가중 값을 **나란히** 둘 뿐이다.
- 표본은 `adherenceRate` 와 **같다**(종결 실행) — 두 지표가 다른 집합을 보면 나란히 놓는
  의미가 없다. `plannedMinutes` 가 분모 집합, `completedMinutes` 가 분자 집합의 계획 시간 합.
- `actualMinutes / completedMinutes` 가 "예상이 맞았나" 다(1.0 = 예상대로, 1.3 = 30% 더
  걸림). **완료한 실행만** 센다 — 중단된 실행의 소요는 계획 시간과 비교할 대상이 아니다.
- 계획 길이는 카드의 `estimatedMinutes` 가 아니라 **블록 시각**(`planEndAt - planStartAt`)
  에서 파생한다. 주간 편집기로 블록을 옮기거나 리사이즈하면 둘이 갈라지는데, 그 주에 실제로
  계획돼 있던 시간은 블록 쪽이다.
- **`period_summaries` 에 저장하지 않는다** — `mandala`/proposals 와 같이 조회 시점에
  파생한다. 그 주의 `execution_events` 만 있으면 언제든 다시 셀 수 있어 저장할 이유가 없고,
  덕분에 마이그레이션이 없다. precomputed 경로와 즉석 계산 경로가 **같은 함수**를 쓴다.
- 길이를 모르는 옛 실행(`planEndAt` 없음 등)은 0 으로 세지 않고 합계에서 뺀다 — 0 으로 세면
  분모가 조용히 부풀어 준수율이 낮게 나온다.

## v1.98 — 2026-08-28 (미체크 배지 유예를 블록 길이에 비례로 — ADR-0009 D5)

**동작 변경 — `GET /today/agenda`.** 응답 형태는 그대로다(`missedCheckIn` 은 여전히 boolean).
그 값이 `true` 로 바뀌는 **시점**이 블록 길이에 따라 달라진다. FE 변경 불필요.

### 무엇이 문제였나

`missedCheckIn` 은 `startAt` + **고정 20분**이었다. 계획 세션이 전부 비슷한 길이일 때는
문제가 안 됐지만, 길이가 작업 내용을 따라가면(v1.96) 짧은 블록에서 판정이 무의미해진다.

**15분짜리 블록은 끝나고 5분 뒤에야 미체크로 잡힌다.** 그 배지는 "지금 시작하라" 는 신호가
아니라 "이미 지나갔다" 는 사후 통보다. 시작을 유도할 수 없으니 사용자가 할 수 있는 일이
없고, 배지는 영영 사라지지 않는다.

### 이제

```
유예 = 블록 길이 × 0.3,  단 [5분, 20분]
```

| 블록 길이 | 유예 | 종전 |
| --- | --- | --- |
| 15분 | 5분 | 20분 (블록이 끝난 뒤) |
| 30분 | 9분 | 20분 |
| 50분 | 15분 | 20분 |
| 67분 이상 | **20분** | 20분 (동일) |

- ⚠️ **상한 20분은 그대로다.** 근거 대장 §6.2 T1 이 그 값을 명시했으므로, 이 변경은 그 선을
  넘지 않는 방향으로만(짧은 블록의 오탐 제거) 완화한다. 비례만 적용하면 2시간 블록이 36분이
  되어 잠금된 값보다 느슨해지는데, 상한이 그걸 막는다.
- 기준은 카드의 `estimatedMinutes` 가 아니라 **블록의 실제 길이**다. 사용자가 주간 편집기
  (`PATCH /plans/{planId}/blocks/{blockId}`)로 블록 길이를 바꾸면 둘이 갈라지고, 배지가
  가리키는 대상은 블록이다.
- 길이를 모르는 호출자에게는 종전대로 20분(하위호환).

## v1.97 — 2026-08-28 (하루 상한 정합 + 재계획 배선 — ADR-0009 D3)

**동작 변경 — `POST /plans/generate`, `POST /plans/replan`.** 요청·응답 형태는 그대로다.
블록이 놓이는 **날짜·시각**이 달라진다.

### 무엇이 문제였나

**① 하루 상한이 '가능한 최댓값' 을 따라갔다.** `daily_cap_for_plan` 은
`max(density 프리셋, 집중 가능 시간)` 이었다. 길이가 균일할 때는 그 둘이 같은 뜻이었지만,
길이가 작업 내용을 따라가면(v1.96) 집중 가능 시간은 *가능한* 최댓값일 뿐 계획에 실제로
등장하는 길이가 아니다. 집중 용량 240분인 사용자의 이번 계획이 30~90분 카드로만
이뤄졌는데도 상한이 240으로 올라, 프리셋(180)이 허용하는 것보다 하루에 더 쌓였다.

**② 재계획이 첫 계획의 배선을 세 가지나 빠뜨렸다.** `POST /plans/replan` 은
`build_forward_replan` 으로 재배치하는데, First Plan 이 쓰는 것 중 셋이 빠져 있었다 —
그래서 첫 계획에서 지킨 것들이 **매주 재계획 때 리셋**됐다.

### 이제

- **하루 상한 = `max(density 프리셋, 이번 계획의 최장 세션)`.** 필요한 보장은
  `상한 ≥ 최장 세션` 뿐이므로 딱 그만큼만 올린다.
- **재계획도 First Plan 과 같은 세 배선을 쓴다:**
  · 그 날 **이미 확정된 집중 시간**을 하루 상한에 이어 센다(#190). 예전엔 상한이 매번 0에서
    시작해, 오전에 5시간을 확정한 날에 또 얹었다.
  · 1차 배치는 확정 블록 앞뒤로 **휴식 여백**을 둔 뷰에서 고른다(#191). 예전엔 진행 중인
    일정에 0분 간격으로 딱 붙었다.
  · 하루 상한을 **후보 최장 세션**까지 올린다(위 ①과 같은 이유).
  셋 다 회피 대상 중 **확정 블록만** 대상이다 — 수면·점심·수업은 '쉴 수 없는 시간'이지
  집중 작업이 아니라, 상한에 넣으면 하루가 통째로 소진되고 여백을 덧대면 기상 직후·수업
  직후 시간이 날아간다.

### 하지 않은 것

ADR-0009 D3 은 "짧은 카드를 자투리 free 조각에 넣는 **3차 패스**" 도 제안했으나
**구현하지 않았다.** 시뮬레이션 결과 기존 2패스가 이미 그 일을 하고 있다 — 평일 09~21시가
수업·알바로 찬 빡빡한 일정에 20~120분이 섞인 카드 20개를 넣어도 **배치 실패 0건**이었고,
저녁 피크가 모자랄 때는 2차 패스가 낮 공강(30분·20분)에 짧은 카드를 6개까지 넣었다.
없는 문제를 위해 패스를 늘리지 않는다.

## v1.96 — 2026-08-28 (세션 길이가 작업 내용을 따라간다 — ADR-0009 D2)

**동작 변경 — `POST /plans/generate`.** 요청·응답 형태는 그대로다. `actionItems[].estimatedMinutes`
값의 **분포**가 달라진다.

### 무엇이 문제였나

계획의 모든 세션이 사실상 같은 길이였다. 네 곳이 그렇게 만들었다 —
분해 프롬프트("세션 길이와 **같거나 비슷하게**", "**절반보다 짧게 만들지 마라**"),
길이 정규화(상한이 **평균**이었다), 검토 LLM("집중 가능 시간과 **크게 어긋나지 않는가**"),
그리고 개수 기반 용량 산정(v1.95 에서 이미 고침).

그래서 '증명서 발급 신청' 과 '자기소개서 초안 작성' 이 같은 길이가 됐다. 예상 시간이 실제와
어긋나면 그 어긋남은 계획에서 끝나지 않는다 — 주간 용량 계산, 미체크 판정(고정 20분),
회복 카드 크기가 전부 그 값을 읽는다.

### 이제

- **길이는 작업에 실제로 걸리는 시간**이다. 지키는 것은 세 가지뿐:
  상한 = 사용자의 집중 가능 시간, 하한 = 15분, 합계 ≈ 그 구간의 가용 시간.
- **정규화 상한이 평균에서 집중 용량으로 올라갔다.** 평균을 상한으로 쓰면 평균보다 긴 세션이
  구조적으로 불가능해 길이가 내용을 못 따라간다. 볼륨은 v1.95 의 분 예산이 지킨다.
- ⚠️ **`goals.session_length` 미답 사용자도 이제 클램프된다.** 예전엔 통째로 no-op 이라
  9분짜리 garbage 도, 집중 용량을 한참 넘는 값도 그대로 나갔다. 전역 `energy.focus_duration`
  (없으면 기본값)이 상한이 된다.
- **세션 개수 규칙이 경로별로 갈린다** — `goals.frequency`(주 N회/매일)로 횟수를 말한 목표는
  개수가 **고정**(그게 사용자가 말한 케이던스다)이고 길이가 그 안에서 흩어진다. 주당 시간만
  준 목표는 개수가 **결과값**이다. 이 문장을 프롬프트에 직접 실어 보낸다.
- **검토 LLM 이 길이 편차를 반려 사유로 쓰지 않는다.** 상한 초과만 본다.

### 실측 (실 Gemini, 프로덕션 게이트 그대로)

시나리오 4종 × 반복 2회. `estimated_minutes` 분포와 `shape_action_plan` 통과 여부:

| 시나리오 | 서로 다른 길이 | 표준편차 | 예산 대비 합계 | 상한 초과 | 잘림 |
| --- | --- | --- | --- | --- | --- |
| 유학 준비(평균=상한) | 3종 | 18.7 / 19.2 | 92% / 90% | 0 | 0 |
| 포트폴리오(평균=상한) | 4종 / 3종 | 9.6 / 18.7 | 96% / 92% | 0 | 0 |
| 취업 준비(평균<상한) | 8종 / 4종 | 16.5 / 13.0 | 99% / 101% | 0 | 0 |
| 볼륨 경로(빈도 없음) | 5종 / 4종 | 27.8 / 12.4 | 100% / 99% | 0 | 0 |

v1 은 같은 입력에서 **표준편차 0.0 · 길이 1종**(전부 120분)이 나왔다.

검토 LLM 은 20~120분이 섞인 계획에 대해 **v2 가 3회 중 1회 반려**했고(사유: "집중 가능
시간이 51분이라 하셨으니 120분 항목을 50분으로 나누세요" — 평균을 상한으로 읽었다),
**v3 는 3회 모두 승인**했다.

### 함께 고친 것

프롬프트가 개수를 "예상치" 로만 알려주자 LLM 이 주 3회 목표에 19개를 만들었고, 케이던스
상한(12개)이 7개를 잘라 **예산 1440분 중 810분(56%)만 남았다**. 룰이 나중에 자르는 것으로는
볼륨을 되살릴 수 없어, 개수 고정 여부를 프롬프트가 알게 했다(위 '세션 개수 규칙').

**동작 변경 — `POST /plans/generate`.** 요청·응답 형태는 그대로다.

### 무엇이 문제였나

계획 분량의 자르기·보충·배치 창이 전부 **세션 개수**를 셌다. 모든 세션이 같은 길이라는
전제인데, 그 전제는 `goals.session_length` 를 답한 사용자에게만 성립한다 — 미답이면
길이 정규화가 no-op 이라 LLM 이 낸 값이 그대로 통과한다.

그래서 주당 시간을 말한 사용자가 손해를 봤다. **주 6시간 · 세션 90분** 목표에서 개수 목표는
4세션인데, LLM 이 20분짜리 8개(=160분)를 내면 개수 상한이 절반을 잘라 **80분**만 남겼다 —
6시간을 말한 사람에게 1.3시간을 준 셈이고, 잘린 4개는 시간 예산 안에 충분히 들어갔다.
반대 방향도 있다: 개수만 맞으면 세션이 아무리 길어도 통과해 주당 시간을 몇 배씩 넘겼다.

### 이제

- **자르기 상한이 분이다** — `주당 세션 수 × 계획 세션 길이 × 지평 주 수`. 앞에서부터 누적 분이
  예산에 닿는 지점에서 자른다(분해 순서 = 의존 순서라 중간을 건너뛰지 않는다).
  세션 하나가 예산보다 길어도 **첫 장은 남긴다**(계획이 통째로 비는 것보다 낫다).
- **케이던스는 여전히 개수로 지킨다** — `goals.frequency`(주 N회/매일)로 횟수를 명시한
  목표는 개수 상한이 **함께** 걸린다. "주 3회"는 한 번이 10분이든 2시간이든 주 3회다.
  주당 시간만 준 목표는 그 개수가 시간에서 나온 파생값이라 분 상한만 건다.
  둘 다 있으면 **먼저 닿는 쪽**이 이긴다 — 어느 쪽도 사용자가 말한 값을 넘기지 않는다.
- **보충(회차 잇기)도 같은 규칙** — 개수가 모자라도 시간이 찼으면 더 붙이지 않고, 반대면
  빈 시간만큼만 채운다. 한 세션도 안 들어가면 '이어가기' 묶음 자체를 만들지 않는다.
- **배치 창 너비**(`days_needed`)도 개수가 아니라 총 분으로 잡는다 — 예전엔 10분 20개와
  180분 20개가 같은 창을 받아, 후자가 하루 상한에 막혀 배치 2차 패스로 통째로 밀렸다.
- ⚠️ **세션 길이가 균일한 동안에는 결과가 종전과 정확히 같다.** 조합 전수 비교로 확인했다
  (빈도 × 주당시간 × 세션길이 × density × 마감 × 지평 × 분해량 = 21,000 케이스, 불일치 0).
  길이를 실제로 갈라놓는 건 다음 조각(ADR-0009 D2)이고, 이 변경은 단위만 바꾼다.

- **DOWNSCOPE = 원본의 40%** 를 5분 눈금으로 반올림하고

- `minRecoveryUnitMinutes` **필드의 의미는 불변** — 전략의 최소 회복 단위이고, 이제 카드

## v1.93 — 2026-08-27 (4주 계획이 목표 전체를 끝내버리던 결함 — ADR-0007 PR-5)

**동작 변경 — `POST /plans/generate`.** 요청·응답 형태는 그대로다.

### 무엇이 문제였나

로컬 최신 main + 실 LLM 으로 인터뷰를 완주시켜 확인했다. 마감까지 **14주 · 84시간**짜리
목표("React 포트폴리오 만들어서 배포")인데, **4주 · 24시간** 계획이 마일스톤 4개를 전부
소진했다 — 12번째 세션이 이미 "이력서 기재용 문구 작성" 이었다. 그런데 같은 응답의
경고문은 이렇게 말한다:

> 그 뒤는 매주 재계획에서 진행 상황을 보고 **이어서 채웁니다** — 빠뜨린 게 아니에요.

**이어서 채울 게 없다.** 사용자는 84시간짜리 목표를 24시간 안에 끝내라는 계획을 받는다.

원인은 분해 프롬프트가 받는 두 지시의 충돌이다 — "확정 마일스톤 **전부**를 branch 로 써라"
와 "이 구간을 총 N개 세션으로 채워라". LLM 은 둘을 **세션을 전 마일스톤에 얇게 펴 발라**
만족시킨다.

### 이제

- `milestones` 를 보내면 이번 계획은 **앞쪽 일부만** 다룬다:
  `round(남은 마일스톤 수 × 이번 창(주) ÷ 마감까지 남은 주)`, 최소 1개.
  · 마감 14주 · 창 4주 · 마일스톤 4개 → **1개** / 마감 8주면 → 2개 / 마감이 창 안이면 전부.
  · 마감이 없으면 자르지 않는다(비율을 낼 기준이 없고, 마감 없는 목표는 애초에 마일스톤
    층을 두지 않는 게 설계다).
- **이미 완료 표시된 앞쪽 마일스톤은 건너뛴다**(v1.90 의 `completedAt`). 이게 없으면 Stage A 가
  매 주기 같은 뼈대를 돌려주므로(v1.82) 분해가 영원히 1번부터 다시 시작한다.
- 범위 밖 마일스톤은 **누락 고지에 안 실린다** — 일부러 안 다룬 것이지 잘려나간 게 아니다.
- ⚠️ **확정 목록 전체는 승인 시 그대로 저장된다.** 좁히는 건 이번 분해에 넘기는 몫뿐이다.

### 세션 내용도 범위를 지킨다

branch 를 룰로 하나만 남겨도 LLM 은 **그 안에서** 뒷 단계를 세션으로 썼다 — 실측: 2주기
12세션 중 **9~12번이 통째로 다음 마일스톤**(Git·Vercel 배포·이력서 기재)이었고 1번은 이미
끝낸 마일스톤의 환경 세팅이었다. 결과는 같다 — 사용자는 여전히 몇 달치를 몇 주에 끝내는
계획을 받는다.

추상 지시("범위를 넘지 마라")는 안 먹혀서, 분해 프롬프트에 **다루면 안 되는 단계의 제목을
그대로** 실어 준다 — 이미 끝낸 마일스톤과 다음 주기가 받을 마일스톤 각각. 실측(3회):
드리프트 **0/3**, 12세션 전부 이번 마일스톤 안.

### 분량은 안 줄어든다 — 단, 되채울 수 있는 목표에서만

잘린 자리는 회차 세션(`{목표} N회차`)으로 다시 채워진다. 실측(같은 인터뷰 5회 반복):
세션 12개 그대로.

⚠️ 그 되채움은 **케이던스를 명시한 목표**(`goals.frequency` = 매일/주 N회)에만 걸린다.
'몰아서·상관없음' 을 고른 목표는 반복이 자연스럽지 않아 회차를 안 붙이는 게 원래 설계라,
거기서 걷어내면 되채울 수단이 없다(실측: 12세션 → 3세션, 경고 0건 —
`volume_shortfall_warning` 은 **배치된 구간** 기준이라 계획이 짧아지면 그 안에서 비율이
맞아 보여 침묵한다). 그래서 **되채울 수 없는 목표에서는 걷어내지 않는다** — 범위가 조금
넓은 계획이 텅 빈 계획보다 낫고, 프롬프트의 제외 목록이 1차로 막는다.

### 걷어낸 단계는 알린다

`warnings` 에 한 줄 나간다 — "'…'는 이번 계획에 넣지 않았어요 … 이어지는 주기에서
받아요". 조용히 빼지 않는 건 대기 단계 고지와 같은 원칙이다.

| | 범위 이탈 | branch | 세션 | 마지막 세션 |
|---|---|---|---|---|
| 전 | **5/5** | 3~4개 | 12 | 매번 "Vercel 최종 배포" |
| 후 | **0/5** | 1개 | 12 | 기초·첫 프로젝트 범위 안 |

⚠️ **만다라에서 승격된 목표는 마일스톤이 전부 완료돼도 이 카드를 못 받는다** — 판정
루프가 승격 목표를 통째로 건너뛴다. 완료 확인이 필요하면 endpoint 를 직접 부르면 된다.

⚠️ **완료해도 그 목표의 카드·알림은 멈추지 않는다.** 이미 배치된 `scheduled_blocks` /
`action_items` 는 목표 상태와 무관하게 조회되므로, 완료를 확정한 뒤에도 남은 카드가
아침 브리프에 그대로 뜬다. 이번 범위 밖이다 — 별도로 다룬다.

이게 없으면 v1.90(마일스톤 완료 표시)이 가드를 살린 뒤로 **다음 주기 제안이 조용히
사라지기만** 하고, 사용자는 목표를 닫을 계기를 못 받는다.

### ⚠️ 동작 변경 — 끝낸 목표는 tier 한도를 안 먹는다

`POST /goals` · `PATCH /goals/{id}` 의 Focus≤3 / Maintain≤5 한도 계산에서
`status='completed'` 인 목표가 **빠진다**. 지금까지는 세고 있었다.

- **왜**: 한도는 "지금 동시에 굴리는 것" 을 제한하는 장치인데, 끝낸 목표가 자리를 계속
  잡고 있으면 **성실히 완주한 사용자일수록 새 목표를 못 만든다.**
- **영향**: Focus 를 꽉 채운 사용자가 하나를 완료하면 새 목표를 만들 수 있게 된다.
  ⚠️ 정정 — 처음엔 "기존에 422 를 받던 요청이 성공할 수 있다" 고 썼는데 **기존 동작은
  한 톨도 안 바뀐다.** `completed` 행이 생길 경로가 이 버전 이전에는 0개였으므로, 실제로
  한도를 먹고 있던 사용자는 존재할 수 없었다. 순수 신규 동작이다.
- ⚠️ **되돌리기(`completed=false`)는 한도를 다시 검사한다.** 안 재면 "완료 → 새 목표 생성
  → 완료 해제" 세 번으로 Focus≤3 을 넘길 수 있다. 한도가 찼으면 422
  `GOAL_TIER_LIMIT_EXCEEDED` 로 거절되고 목표는 완료 상태로 남는다.
- ⚠️ **완료해도 `GET /goals` 목록에는 남으므로**(보관이 아니다) 완료 후 새 목표를 만들면
  그 tier 그룹이 3장을 넘어 보일 수 있다(2 active + 1 completed 배지 + 1 신규). FE 는
  `status` 로 갈라 렌더해야 한다.

### ⚠️ 끝낸 목표는 새 계획 후보에서 빠진다

`POST /plans/generate` 가 heaviest 목표를 고를 때 `status='completed'` 인 목표를 후보에서
제외한다. 안 그러면 완료를 확인한 뒤에도 같은 제목이 후보로 남아, 다음 생성이 그 목표에
새 4주 트리를 붙이고 화면에는 "완료" 배지가 달린 채 카드가 쏟아진다.

같은 제목으로 다시 시작하고 싶으면 `completed=false` 로 되돌리거나 새 목표를 만들면 된다.

## v1.85 — 2026-08-26 (확정한 뼈대의 **변경**이 저장된다 — ADR-0007 PR-6 전반부)

**동작 변경 — `POST /plans/{planId}/approve`.** 요청·응답 형태는 그대로다(필드 추가·삭제
없음). 바뀌는 건 Draft 의 `milestones` 를 승인이 **어떻게 반영하는가**다.

- 지금까지: 그 goal 에 활성 마일스톤이 이미 있으면 Draft 의 목록을 **조용히 무시**했다
  (PR-2 가 "한 번만 만든다"로 좁혀 넣었다). 그래서 v1.82 로 Stage A 가 저장된 뼈대를
  돌려주기 시작한 뒤에도, 사용자가 그 목록을 **고쳐서** 확정하면 계획만 편집본으로
  만들어지고 DB 는 옛것으로 남았다 — 갈라진 채 고칠 수단이 없었다.
- 이제: 확정 목록을 **뼈대 그 자체**로 보고 반영한다.
  - 정규화한 제목(공백 무시)이 같으면 **같은 행을 유지**하고 제목 표기·순서·요약을
    갱신한다. 노드 id 와 `completedAt` 이 보존된다 — 순서 한 번 바꿨다고 진척이 날아가면
    안 된다. **표기는 갱신한다** — 대조는 공백을 무시하지만 화면에 보이는 건 사용자가
    확정한 제목이라, `"기초문법"` → `"기초 문법"` 같은 편집도 저장된다.
  - 확정 목록에서 빠진 것은 **보관**(archive)한다. 지우지 않는다.
  - 새 제목은 삽입한다.
  - 같은 목록을 다시 승인하면 아무것도 만들지도 보관하지도 않는다(**멱등**).

**입력 정규화 2가지**(둘 다 승인이 조용히 처리한다 — 오류를 내지 않는다):

- **제목이 비었거나 공백뿐인 항목은 버린다.** `title` 에 길이 제약이 없어 확인 화면에서
  제목 칸을 비우고 확정하면 그대로 들어오는데, 그런 항목은 대조 키를 만들 수 없어
  **승인할 때마다 새로 만들어지고 옛것은 보관돼** 행이 무한히 늘어난다.
- **한 목록 안에 정규화가 같은 제목이 두 번 오면 처음 것만 남긴다**(`"기초 문법"` 과
  `"기초문법"` 은 같은 것). 두 행을 만들어 두면 다음 승인의 대조에서 하나가 밀려나
  `completedAt` 을 안은 채 보관된다.
- `activatedGoalNodes` 는 이번 4주 트리 + **새로 만든** 마일스톤 수의 합이다(유지·보관된
  것은 안 센다). 뼈대를 그대로 두고 재승인하면 이 값이 4주 트리 수와 같아진다.

### ⚠️ 빈 목록은 삭제가 아니다

`milestones` 가 비어 있으면 **뼈대를 건드리지 않는다.** "이번엔 마일스톤 없이 세운다"
(Stage A 건너뜀)를 FE 가 빈 목록으로 표현하기 때문이다. 이걸 삭제로 해석하면 뼈대를 가진
사용자가 한 번 건너뛰는 순간 마감까지의 계획 축이 사라진다. **뼈대를 비우는 입력은 아직
없다** — 필요해지면 별도 표현을 만든다.

### ⚠️ 개명은 "삭제+추가"와 구별되지 않는다

제목이 곧 식별자다. 서버가 발급한 id 를 FE 가 왕복시키는 설계(ADR-0007 §10)는 **아직 안
넣었다** — FE 가 지금 `{title, summary}` 만 만들어 보내고, 그 식별을 소비할 곳(leaf ↔
마일스톤 링크)도 아직 없다. 소비자가 생길 때(PR-3 진척 롤업) 함께 넣는다.

실질 영향: 사용자가 마일스톤 제목을 고치면 옛 행이 보관되고 새 행이 생긴다. 지금은 그
행을 참조하는 것이 없어 결과가 같지만, PR-3 이후에는 그 마일스톤에 달린 진척이 함께
끊긴다. **PR-3 이 §10 을 선행 조건으로 갖는다.**

## v1.70 — 2026-08-23 (인터뷰 명료성 지표 — 유도 슬롯 누수 수정)

**버그 수정(하위호환)** — endpoint·스키마 변경 없음. `GET /interview/sessions/{id}` 등
인터뷰 응답의 `ambiguityScore` **값**만 바뀐다.

### 증상

계획 인터뷰가 정상 종료(`endReason="completed"`, `outcome.unresolvedSlots=[]`)해도
`ambiguityScore` 가 **1** 로 남았다 — 서버가 "다 끝났다"와 "아직 1개 남았다"를 동시에 말했다.

⚠️ **화면이 100%에 못 닿는다는 뜻은 아니다.** FE(`GoalIntakeScreen`)가 이미
`isFinished ? 100 : ...` 로 **종료 시 100%를 강제**하고 있었다 — 그 코드 주석이 이 버그를
그대로 적어 두고 있다("서버는 남은 필수 슬롯이 있어도 outcome 을 싣고 completed 로
마감한다"). 즉 클라이언트가 서버의 잘못된 값을 가려 주고 있었고, 실제로 어긋난 것은:

- **API 계약** — 종료 응답이 자기 모순(`unresolvedSlots=[]` 인데 남은 수는 1)
- **인터뷰 중 진행률** — 유도가 성립한 뒤로 끝까지 한 슬롯(약 5.5%)만큼 낮게 표시
- `ambiguityScore == 0` 을 완료 신호로 쓰는 **모든 소비자**(FE 외 클라이언트·테스트·모니터링)

### 원인 — 같은 판정을 세 곳이 손으로 따로 조립했다

"미해결 필수 슬롯" 판정은 세 곳이 쓴다. 셋 중 **FE 지표만** 유도 규칙(`is_slot_needed`)을
빠뜨리고 `is_filled_answer` 로만 셌다:

| 쓰는 곳 | 유도 슬롯 제외 | 결과 |
|---|---|---|
| FSM `_next_required_slot`(다음 질문) | O | `goals.weekly_time` 을 묻지 않음 |
| `build_outcome.unresolvedSlots` | O | 빈 배열 |
| `_remaining_required`(→ `ambiguityScore`) | **X** | 영원히 1 |

`goals.weekly_time` 은 `goals.session_length × goals.frequency` 로 유도되면 질문 자체가
나가지 않는다(v1.5x, 주당 총량을 곱셈으로 되묻지 않기 위함). **묻지 않은 슬롯을 지표만
세니** 사용자가 채울 방법이 없었다.

### 수정

판정을 `interview_adapter.open_required_keys(required_keys, slot_answers)` **한 함수**로
모으고 네 곳(위 셋 + `build_ultimate_outcome`)이 그것만 부르게 했다. 다음 유도 슬롯이
생겨도 갈릴 자리가 없다.

### 계약 영향

- 정상 종료 시 `ambiguityScore` 는 **항상 0** (이전엔 유도 성립 시 1).
- `plan` 에서 실제로 묻는 필수 슬롯은 **17 또는 18** — 빈도를 '몰아서 · 상관없음' 으로 답해
  주당 시간을 계산할 수 없으면 그 슬롯을 실제로 물으므로 18이다.
- **FE 변경은 필요 없다.** 진행률 분모(`initialAmbiguity`)를 **세션 시작 응답의
  `ambiguityScore`** 에서 가져오는데(`GoalIntakeScreen`), 시작 시점엔 유도가 성립하기 전이라
  그 값은 그대로 18이다. 진행 중 표시가 정확해질 뿐이다.
- 다만 FE 의 `isFinished ? 100 : …` 강제는 이제 **불필요**하다 — 서버가 0을 준다. 지워도
  되고 그대로 둬도 무해하다(방어로 남길 만하다).
- 분모를 코드에 **상수로 박아 둔** 클라이언트가 있다면 그쪽은 어긋난다. 분모는 세션 시작
  응답에서 받고, 완료 판정은 `ambiguityScore == 0` 을 쓰는 편이 안전하다.

- **다른 목표의 계획과 딱 붙지 않는다**(#191). 계획 **안에서는** 카드 사이에 휴식(`break_min`)을
  두면서 계획 **사이에는** 0분이었다. 실측: `19:15~21:15` → `21:15~22:15` → `22:15~23:15`,
  휴식 없는 4시간 연속. 이제 기존 승인 블록 앞뒤로 휴식 여백을 두고 배치한다
  (`20:00~22:00` → `22:10~23:10`).
  - 여백은 **1차 배치에만** 적용한다. 하루가 빡빡하면 여백을 포기하고 붙여서라도 배치한다 —
    여백 때문에 세션이 통째로 빠지면 안 되기 때문이다.
  - 수면·고정일정에는 덧대지 않는다. 그건 '집중 작업'이 아니라 '쓸 수 없는 시간'이고,
    여백을 주면 기상 직후·수업 직후가 통째로 날아간다.
- **`warnings[]` 에 항목 추가** — 하루 총량이 상한을 넘긴 날이 있으면 알린다.
  예: `"7월 30일은 집중 시간이 약 4.0시간으로 평소 기준(3시간)보다 많아요. 마감까지 담으려면
  이만큼이 필요해서예요 — 부담되면 일부를 다음으로 미뤄도 괜찮아요."`
  상한 초과는 마감이 임박할 때 세션을 떨어뜨리지 않으려는 **의도된 동작**이지만, 말해주지
  않으면 사용자는 4시간짜리 하루를 이유 없이 마주친다. 가장 무거운 하루 하나만 짚는다.
- 응답 스키마 변경 없음. 배치 결과(날짜·시각)가 달라지는 동작 변경이다.
