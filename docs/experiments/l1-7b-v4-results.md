## 0. 이 문서가 주장하는 것과 주장하지 않는 것

**v4 의 목적은 v3 의 미탐을 고치는 것이 아니었다.** 이유·유형·노드 지목을 **측정 가능하게**
만드는 것이었고, 그것은 됐다.

> **M27b·M27gap·M28a·M28b 를 이 프로젝트에서 처음으로 산출했다.** v3 는
> `{approved, feedback: list[str]}` 뿐이라 자유 문장을 기계가 셀 수 없었다.

⚠️ **v3 대 v4 를 성능 비교로 읽으면 안 된다.** 한 번에 **네 가지를 동시에 바꿨다** —
출력 계약(자유 문장 → 구조화 finding) · 승인 주체(LLM → 코드) · 변수 집합(6종 → 2종) ·
카드에서 `estimated_minutes` 제거. 어떤 차이도 **어느 변경 때문인지 귀속할 수 없다.**

⚠️ **계산 가능(computable) ≠ 추정 가능(estimable).** 유형별 `easy` 표본이 **2건**이다.
M27b·M27gap·M28a·M28b 에는 **신뢰구간을 붙이지 않았다.** 계획서가 요구한 "M29 ≤0.10 제약
하 최대 recall" 운영점 선택은 이 표본으로 **불가능**하다. v4 가 연 것은 **구조**이지
결론이 아니다.

⚠️ **v4 는 평가 후보이지 프로덕션이 아니다.** ④층 `review_plan` 은 여전히 v3 를 부른다.
승격 조건은 §7 에 적는다.

## 1. 무엇을 어떻게 쟀나

| | v3 (기준선) | **v4 (이 실행)** |
|---|---|---|
| 출력 | `{approved, feedback: list[str]}` | `{findings: [{defect, severity, node_id, message}]}` |
| 승인 판정 | **LLM 이 한다** | **코드가 한다** — `severity >= 2` 존재 여부 |
| 넘기는 변수 | 6종 (`focus_capacity`·`session_length` 포함) | **2종** — 목표 트리와 카드뿐 |
| 카드 `estimated_minutes` | 넘어감 | **제거** (§8) |
| 산출 가능 지표 | M27a · M29 · M32 | **+ M27b · M27gap · M28a · M28b** |

`focus_capacity`·`session_length` 를 뺀 근거는 루브릭 §1.2 다 — ③층
`normalize_action_minutes` 가 이미 불변식으로 보장해 상한 초과는 보정 후 **0/1,620**
(구조적으로 발화 불가)이고, 그 항목의 반려는 **정의상 전부 오탐**이다.

**표본 단위는 v3 와 같다.** 주 지표의 1차 추정은 사전 지정된 `PRIMARY_REPEAT = 0` 의 고유
케이스다. 반복 3회를 150개 독립 표본으로 세지 않는다.

**지표 분모는 §5 가 정한다.** `easy` 한정 · severity 게이트 공통 · 지어낸 노드 처리 —
셋 다 실험계획서 §5 에 확정 문단으로 기록했다. 하네스가 아니라 §5 가 진실 소스다.

## 2. 계약 준수 — 이게 나쁘면 아래 수치를 읽을 수 없다

```
룰 폴백                    0 / 150
계획에 없는 node_id        0 / 16 finding      ← 지어낸 노드 없음
스키마 위반                0 / 150             ← severity 범위·결함 코드 전부 유효
```

**16건 전부가 입력 계획에 실재하는 `node_id` 를 지목했다.** 하네스는 없는 id 를 조용히
받지 않는다 — 지어낸 노드는 M28b 분자에서 빠지되 **분모에는 남는다**(면제가 아니라 실패).
이번 실행에서는 그 경로가 한 번도 발화하지 않았다.

⚠️ 다만 **유형 지표(M27b·M28a)는 위치를 보지 않는다.** 지어낸 노드를 짚은 finding 도 유형
적중으로는 계상된다 — 정의상 분리된 능력이라 그렇게 뒀고, 그래서 스키마 준수율을 지표들보다
**먼저** 싣는다.

## 3. M29 — 이 표본에서는 임계값을 확인했다

```
오반려          0/30 = 0.000
단측 95% 상한   0.095        ← Clopper-Pearson (정확값)
사전등록 기준   ≤ 0.10       → **이 표본에서 확인**
```

**더 강한 사실이 하나 있다.** repeat 0 뿐 아니라 **대조군 90행(30건 × 3반복) 전체에서
finding 이 단 한 건도 나오지 않았다.** 16건 전부 결함 케이스에서 나왔다.

⚠️ **그래도 "v4 가 v3 의 오탐을 고쳤다" 고 말하지 않는다.** v3 는 1/30, v4 는 0/30 —
**케이스 한 건 차이**다. n=30 에서 1→0 은 통계적으로 구별되지 않고, §0 의 이유로 네 변경 중
어느 것의 효과인지도 모른다.

말할 수 있는 것: **이 고정 골든셋 30건에서 v4 는 정상 계획을 한 번도 반려하지 않았고,
그 결과 사전등록 임계값 ≤0.10 을 확인했다.**

## 4. 결함 탐지 — **처음으로 "왜" 를 볼 수 있다**

**repeat 0, 유형별.** easy 의 정답은 반려, boundary 의 정답은 통과다. **유형별 n=2 다.**

| 유형 | M27a easy 반려 | **M27b** 옳은 유형 지목 | boundary 오탐 |
|---|---|---|---|
| **D1** 중복 | 2/2 | **2/2** | 0/2 ✓ |
| **D2** 착수 불가 | 0/2 | **0/2** | 0/2 ✓ |
| **D3** 순서 역전 | 1/2 | **1/2** | 0/2 ✓ |
| **D4** 착수 단서 부재 | 1/2 | **1/2** | 0/2 ✓ |
| **D5** 목표 무관 | 1/2 | **1/2** | 0/2 ✓ |
| **합계** | **5/10** | **5/10** | **0/10** |

### 4.1 M27gap = 0/5 — 이것이 v4 가 처음 알려주는 것

```
M27gap `wrong_reason_rate`    0/5     ← 반려한 5건 전부 **옳은 결함 코드**를 지목했다
M28a  `verifier_type_id`      5/5
M28b  `verifier_localization` 3/3     ← 위치 누출 2건 제외 후 (제외 없이 세면 5/5)
```

**반려할 때는 틀린 이유로 반려하지 않았다.** v3 로는 이 질문 자체를 물을 수 없었다 —
자유 문장이라 "무엇을 왜 지적했는지" 를 기계가 셀 수 없었기 때문이다.

⚠️ **분모가 5건이다.** M27gap·M28a 는 **반려된 건**이 분모라 탐지가 적으면 분모도 같이
작아진다. `0/5` 를 "이유 정확도 100%" 로 읽지 마라 — **다섯 건에서 틀리지 않았다**는 뜻이다.

⚠️ **M28b 는 3건에서만 잰 값이다.** easy 반려 5건 중 `d1-easy-portfolio`·`d5-easy-cert`
두 건이 위치 누출 목록에 있어 분모에서 뺐다. 제외 목록은 코드가 한 곳에서 만든다 —
`check_seeded_defect_shortcuts.m28_leaked_case_ids`.

✅ **다만 이번 실행에서는 그 누출 경로가 애초에 닫혀 있다** — v4 는 `estimated_minutes` 를
넘기지 않으므로 `argmin(분량)` 을 쓸 수 없다(§8). 그래도 주 지표는 보수적으로 제외 후로 뒀다.
제외 없이 세면 5/5 다.

### 4.2 D2 는 지름길이 있는데도 못 잡는다 — 가장 강한 관찰

D2(착수 불가)는 **easy 2건 모두 반려하지 못했다.** 그리고 `eval/README.md` 는 D2 에 대해
이렇게 적는다:

> **가장 나쁘다.** "계획에 `마저` 가 있으면 D2 결함" 이라는 한 줄 규칙이 오탐 없이 2/2 를
> 맞힌다(무결함 대조군 발화 0건).

**한 줄짜리 문자열 규칙으로 맞힐 수 있는 것을 LLM 검토기가 못 맞혔다.** 이 칸은 지름길
경고와 **무관하게** 읽어도 된다 — 오히려 지름길이 있는데도 0/2 라는 점이 관찰의 강도를
높인다. v3 도 같은 자리에서 0/2 였다.

### 4.3 severity 가 아직 운영점 척도로 못 쓰인다

```
severity 2 → 11건    severity 3 → 5건    severity 1 → 0건
```

| 임계값 | M29 오반려 | M27b recall (easy) |
|---|---|---|
| **≥ 2** | 0/30 | **5/10** ← 기본 |
| ≥ 3 | 0/30 | 2/10 |

**임계값을 3으로 올려도 오탐이 줄지 않고(이미 0) 탐지만 절반 이하로 떨어진다.** 즉 지금
severity 는 **운영점을 고르는 데 쓸 수 있는 척도가 아니다** — 오탐이 이미 바닥이라 교환할
것이 없다. 이걸 볼 수 있게 된 것 자체가 v4 의 산출물이다.

## 5. M32 — 판정 일관성

```
쌍 일치            144/150 = 0.960
판정이 갈린 케이스   3/50
분포               모두 승인 43 · 모두 반려 4 · 갈림 3
```

⚠️ **0.960 을 "안정적" 으로 읽으면 안 된다.** 50건 중 43건이 3회 모두 승인이라
**승인 편향이 pairwise 일치율을 밀어 올린다.** 정확한 서술은 "144/150 쌍이 일치했고
실제로 갈린 것은 3건" 이다. (v3 도 같은 구조였다 — 45/2/3.)

갈린 3건은 `d2-easy-cert`·`d3-easy-portfolio`·`d4-easy-cert` 로 **전부 easy 결함**이다.
흔들림이 **미탐 쪽**에서 난다.

⚠️ 이 셋을 "경계 사례" 라고 부르지 않는다 — 골든셋의 `boundary` 는 정답이 통과인 별도
수준이다. **"결정이 갈린 사례"** 로만 부른다.

⚠️ **D3 의 1/2 는 이 흔들림 위에 있다.** `d3-easy-portfolio` 가 갈린 케이스다. 1차 실행
(폐기분)에서 D3 는 150호출 내내 finding 이 0건이었다. **"분량을 뺐더니 D3 를 보게 됐다" 로
읽으면 안 된다** — 한 건 차이이고, 그 한 건이 회차마다 흔들린다.

## 6. 범위 한계 — **보고서에 반드시 함께 싣는다**

### 6.1 이것은 "일반 결함 발견 능력" 이 아니라 **이 루브릭 준수도**다

심은 결함은 루브릭 §2 의 앵커를 따라 만들어졌고, **v4 프롬프트도 같은 앵커를 싣는다.**
그래서 이 수치는 "루브릭이 정의한 결함을 루브릭대로 찾는가" 를 잰다. **루브릭이 못 적은
실패 유형은 여기서 영원히 측정되지 않는다.**

held-out 완화책은 그대로 유효하다 — 결함 인스턴스는 루브릭 작성자가 아니라 **다른 모델이
설계**했다. 그러나 v4 프롬프트에 앵커를 실은 이상, 이번 축은 v3 때보다 **순환성이 더 크다.**

### 6.2 통제된 비교가 아니다

네 가지를 동시에 바꿨다(§0). v3 대비 어떤 수치 변화도 **원인 귀속이 불가능**하다.
가르려면 한 번에 하나씩 바꾼 arm 이 필요하다 — 예: v3 프롬프트 그대로 두고 변수만 줄인 arm.

### 6.3 표본이 결론을 지탱하지 못한다

| 지표 | 이번 분모 | 문제 |
|---|---|---|
| M27b (유형별) | **2** | 0/2·1/2·2/2 세 값밖에 못 나온다 |
| M27gap · M28a | **5** | 탐지가 적으면 분모가 같이 준다 |
| M28b | **3** | 누출 제외 후 |
| M29 | 30 | 유일하게 상한을 붙일 수 있는 축 |

**M29 를 제외한 어느 지표에도 신뢰구간을 붙이지 않았다.** 붙일 수 없어서다.

### 6.4 그 외

- **전 케이스 합성이다.** 실사용 계획 분포를 대표하지 않는다.
- **남은 지름길 9건**이 그대로다(`eval/README.md`). D1 의 2/2 를 의미 이해의 증거로 읽지 않는다.
- **M30·M31·M33·M34 는 이 실행에 없다.** 재분해를 돌리지 않았고 대조군 arm(④층 제거 ·
  피드백 비운 재분해)도 없다.
- **3반복은 같은 날·같은 모델 버전·같은 설정**이고 시드 통제가 없다.
- ✅ v3 결과가 달고 있던 `conflict_report="(없음)"` 범위 한계는 **v4 에 없다** — 애초에 그
  입력을 안 쓴다. 대신 **충돌을 사용자에게 전달할 통로가 v4 출력 계약에 없다**는 것이
  승격의 미해결 조건이다(§7-1).

## 8. 1차 실행을 폐기한 이유 — 독립 검증이 찾은 입력 계약 결함

같은 날 1차로 150호출을 돌렸고(SHA `7409d1ac…`) **폐기했다.** 독립 검증이 찾은 것:

> **`focus_capacity`·`session_length` 변수는 지웠는데, `action_items` 의 각 카드가
> `estimated_minutes` 를 그대로 싣고 있었다.**

루브릭 §1.2 는 *"프롬프트에 '검사하지 마라'가 아니라 **변수 자체를 넘기지 않는** 방식으로
강제한다 — 변수가 있으면 지시를 어긴다(실측 다수)"* 라고 못박는다. **상한값은 사라졌지만
실현된 분량은 그대로 보였다** — "카드가 전부 120분이다", "길이가 제각각이다" 는 이 값만으로
판단 가능하다. 그것을 막는 것은 오직 프롬프트 문장뿐이었고, 그건 §1.2 가 신뢰할 수 없다고
선언한 바로 그 수단이다.

**같은 필드가 M28b 위치 누출의 원인이기도 했다.** 누출의 정체가
`argmin(estimated_minutes)` 이므로(`_is_unique_non_modal_minutes`), 분량을 안 보여주면
**그 경로 자체가 사라진다.** D1~D5 어느 유형도 분량을 요구하지 않는다.

→ `_STRIPPED_ITEM_FIELDS = ("estimated_minutes",)` 로 카드에서 지우고 **전량 재실행**했다.
`test_estimated_minutes_never_reaches_the_verifier` 가 이 성질을 고정한다.

### 8.1 같은 검증이 찾은 다른 것들

| | 지적 | 조치 |
|---|---|---|
| **집계 함수에 테스트가 0줄** | 누출 제외 삭제 · 지어낸 노드 면제 · easy 한정 해제를 **동시에** 해도 전 테스트 초록이었다(뮤테이션 실증) | `compute_metrics` 순수 함수로 분리하고 테스트 11건 추가. 같은 뮤테이션 4종이 이제 전부 빨강 |

## 9. ⚠️ 구조적 위험 — 프롬프트 이름과 자동 latest

`prompts/registry.py` 의 `latest()` 는 **최고 버전을 자동 선택**한다. 그리고 프로덕션은
버전을 안 붙이고 부른다:

```python
# orchestrator/first_plan.py — ⚠️ 아래는 2026-09-06 **이전**의 코드다
prompt_id="planning/plan_quality",   # ← 버전 없음 → latest

# 현재
prompt_id="planning/plan_quality@v3",   # ← 핀
```

**따라서 `plan_quality.v4.md` 라는 파일을 만드는 것만으로 ④층이 v4 를 부르게 된다.**
출력 스키마가 `PlanReview` 라 파싱에 실패하고 **룰 폴백으로 조용히 강등**된다.

실측으로 확인했다 — 그 이름으로 파일을 두면 기존 테스트 3개가 함께 빨강이 된다.
레포의 기존 테스트 주석도 이 위험을 이미 적어 두고 있었다: *"이 파일이 존재하는 것만으로
latest 가 되어 프로덕션이 조용히 룰 폴백으로 강등된다."*

**그래서 이름을 `plan_quality_eval` 로 분리했다** — 프로덕션 코드를 한 줄도 바꾸지 않고
격리하는 유일한 방법이었다. `test_production_review_still_resolves_to_v3` 가 이 분리를 지킨다.
