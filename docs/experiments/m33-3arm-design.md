>
> **작성 2026-09-04 — 실행 전.** 이 문서가 고정하는 것을 **결과를 보고 바꾸지 않는다**
> (§0.1 정직성 규칙 1번). 바꿔야 하면 **바꾼 사실과 시점을 여기 적고** 그 실행을 별도로 센다.

## 0. 이 실험이 답하는 질문

> **LLM 검토기 층(④)을 두는 것이 순이득인가.**

이건 "검토기를 개선했는가" 가 아니다. **"검토기가 필요한가"** 다. 우리는 ③층에 결정적
검증기를 이미 갖고 있어서 이 비교가 가능하다 — LLM-Modulo(ICML'24)가 권하는 구조가
정확히 "생성은 LLM, 검증은 sound verifier" 다.

**문헌은 부정적 결과를 반복해서 보고했다.** Valmeekam et al. 2023(LLM+VAL 59% vs
LLM+self-critique 41%), Kambhampati & Valmeekam(자기비평이 baseline 보다 **나빠질 수
있다**), Huang et al. ICLR'24(외부 신호 없는 자기수정은 정확도를 **떨어뜨린다**).
**M33 이 음수로 나오는 것은 정상 가능 결과이고, 그걸 그대로 싣는 것이 이 실험의 값이다.**

## 1. 세 arm — 정확한 차이

**동일한 초기 계획을 세 arm 이 공유한다.** 초기 분해를 arm 마다 새로 돌리면 ④층 효과와
분해기 변동이 한 수치에 섞인다.

| arm | 재분해 | `review_feedback` | 무엇을 분리하나 |
|---|---|---|---|
| **A. 없음** | **안 한다** — 초기 계획 그대로 | — | ④층이 없을 때의 계획 |
| **B. 상세 피드백** | 한다 | 검토기가 낸 `feedback[]` 전문 | ④층 + 비평 내용 |
| **C. 빈 피드백** | 한다 | **비운다**(`"(첫 분해 — 이전 피드백 없음)"`) | ④층 + **재시도만** |

```
M33 = M26-core(B) − M26-core(A)     ④층 전체의 순이득
M34 = M30(B) − M30(C)               비평 내용의 순기여 (재시도 효과를 뺀 것)
```

⚠️ **C 가 없으면 M30 을 재시도 효과와 구별할 수 없다.** Stechly et al. 이 상세 피드백과
최소 피드백("다시 해봐")의 결과가 **거의 같음**을 보고했다 — 개선이 비평 내용이 아니라
재샘플링에서 왔다는 뜻이다. 구현 비용은 **문자열 하나를 비우는 것**이다.

⚠️ **B·C 는 재분해 조건이 나머지 전부 동일해야 한다** — 같은 초기 계획, 같은 반려 판정,
같은 모델·온도·thinking budget, 같은 프롬프트. `review_feedback` 변수 **하나만** 다르다.

### 1.1 재분해는 **공통 검토 결과가 "반려" 일 때만** 일어난다

세 arm 이 **같은 초기 계획 + 같은 검토 판정**을 공유한다. 그 판정이 **승인**이면
**B·C 도 재분해하지 않고 최초 계획을 보존한다** — 프로덕션 `should_replan` 이 그렇게
동작하므로, 반려가 아닌데 재분해하면 **제품 흐름과 다른 것을 비교**하게 된다.

```
검토 = 승인  →  A · B · C 모두 초기 계획 그대로 (셋이 동일)
검토 = 반려  →  A 는 그대로 · B 는 feedback 으로 재분해 · C 는 빈 피드백으로 재분해
```

**따라서 ΔM26-core 는 반려된 케이스에서만 움직인다.** 승인 케이스는 세 arm 이 같으므로
Δ 에 0 을 기여한다 — 그 수를 결과에 함께 적는다.

### 1.2 A arm 은 "검토기를 안 부른다" 가 아니다

검토기는 **부르되 그 결과로 재분해하지 않는다.** 그래야 세 arm 이 **같은 반려 판정**을
공유하고, B·C 의 재분해 대상 집합이 A 와 같아진다. 검토기를 아예 안 부르면 어느 케이스가
반려됐는지 모르므로 **M30 의 분모("반려된 케이스")가 정의되지 않는다.**

## 2. 실행 순서 — arm 별로 교차한다

```
case1-A · case1-B · case1-C · case2-A · case2-B · case2-C · …
```

**한 arm 을 몰아서 돌리지 않는다.** 모델 버전·시간대·서비스 상태 변동이 한 arm 에만
실리면 그 변동이 arm 효과로 읽힌다. 케이스 단위로 A→B→C 를 붙여 돌린다.

⚠️ 그래도 **같은 날 안에서 끝낸다.** 날짜가 걸치면 마감 오프셋이 달라진다
(`deadline_offset_days` 는 상대값이라 실행일이 바뀌면 다른 계획이 된다).

## 3. 표본 — 일반 34건과 **challenge stratum 을 분리**한다

### 3.1 왜 challenge stratum 이 필요한가

현재 **M26-core = 0.794 (27/34)** 다. 실패가 **7건뿐**이라 긍정적 개선폭이 구조적으로
**최대 7/34 = 0.206** 으로 제한된다. **천장 효과**다 — ④층이 아무리 좋아도 그 이상 못 올린다.

### 3.2 ⚠️ 실패한 7건을 골라 쓰면 안 된다

그건 **결과를 보고 표본을 고르는 것**이다. challenge stratum 은 **입력 조건으로 정의**한다 —
어떤 케이스가 실패했는지 **모르는 상태에서도 같은 집합이 나와야 한다.**

### 3.3 입력 조건 격자 — **양쪽 값이 전부 정확한 수다**

**결과가 아니라 슬롯 값만으로 결정된다.** 생성기를 돌리면 어떤 케이스가 실패했는지
몰라도 같은 16건이 나온다.

생성기: [`scripts/build_challenge_stratum.py`](../../scripts/build_challenge_stratum.py) ·
산출: `eval/golden_challenge_stratum.jsonl` (**결정적이라 커밋한다**)

| 축 | 어려움 | 쉬움 |
|---|---|---|
| **경계** | `session_length = 120` (집중용량과 **같다**) | `session_length = 90` |
| **빈도** | `frequency_per_week = 7` | `frequency_per_week = 3` |
| **활동창** | `21:00-22:00` (**60분**) | `09:00-23:00` (840분) |
| **마일스톤** | 2개 | 0개 |

**전 케이스 공통**: `focus_duration_min = 120` — 경계 축이 `session_length` 하나로만 갈리게.

**`weekly_hours = round(frequency × session_length ÷ 60)`.**

⚠️ **반올림 때문에 축이 깨끗하게 분리되지 않는다.** `weekly_hours` 는 스키마가 **정수 시간**
이라 반올림이 불가피하고, 그러면 **파생 세션 길이가 선언값과 어긋난다**:

| 경계 | 빈도 | 선언 `session_length` | `weekly_hours` | 파생 세션 |
|---|---|---|---|---|
| hard | 3 | 120 | 6 (정확) | **120** ✓ |
| hard | 7 | 120 | 14 (정확) | **120** ✓ |
| easy | 3 | 90 | 4 (4.5 → 4) | **80** ✗ |
| easy | 7 | 90 | 10 (10.5 → 10) | **86** ✗ |

**따라서 `easy` 경계 쪽에서는 빈도를 바꾸면 세션 길이도 80↔86분으로 함께 바뀐다.**
초판이 *"세션 길이를 빈도와 무관하게 일정하게 만든다"* 고 쓴 것은 **과장이었다** — hard
쪽에서만 성립한다.

**정확한 표현**: `frequency_per_week` 는 **케이던스**(며칠 하느냐)이고 `weekly_hours` 는
**근사적인 볼륨**이다. 둘이 세션 길이를 함께 결정하므로 **완전히 직교하지 않는다.**

⚠️ **`>=` · `<=` 를 남기지 않는다.** 범위로 적으면 나중에 5/6/7 중 무엇을 고를지 여지가
남는다. `tests/test_challenge_stratum.py` 가 양쪽 값을 정확한 수로 고정한다.

#### ⚠️ 초판의 활동창 축은 틀렸다 (2026-09-04 정정)

초판은 **"≤ 6시간"** 이라는 **절대 시간**으로 적었다. 실측하니 **변별력이 0** 이었다:

```
활동창 09-23시(14h) → 20세션 전부 배치
활동창 21-22시(1h)  → 20세션 전부 배치      ← 24분 세션이 하루 하나씩 들어간다
```

**활동창은 세션 길이보다 짧을 때만 물린다.** 그래서 **상대 조건**으로 다시 정의했고,
위 값은 그것이 성립하는 정확한 쌍이다(60분 창 < 120분 세션).

⚠️ **더 나쁜 것이 있었다.** 두 outcome builder 가 활동창을 **`09:00-23:00` 으로
하드코딩**하고 있어서, 케이스에 무엇을 넣든 스케줄러에 **전혀 반영되지 않았다.**
입력 계약(`activity_start`/`activity_end`)에서 읽도록 고쳤고 회귀 테스트를 붙였다.

#### 격자 커버리지 확인 (룰 전용 계획 기준, 16건)

⚠️ **이 표를 인과적인 "축 효과" 로 읽으면 안 된다.** 위 반올림 때문에 경계 축을 바꾸면
**주당 볼륨과 파생 세션 길이도 함께 바뀐다.** 이 표가 말하는 것은 *"이 격자가 통과·실패를
모두 만들어 내는가"* 뿐이고, 한 축을 단독 원인으로 귀속할 수 없다.

| 축 (hard vs easy) | M20 실패 | M21 실패 | |
|---|---|---|---|
| 경계 | 6/8 vs 6/8 | 4/8 vs 4/8 | 갈리지 않음 |
| 빈도 | **8/8 vs 4/8** | 4/8 vs 4/8 | M20 이 갈림 |
| 활동창 | **8/8 vs 4/8** | **8/8 vs 0/8** | 양쪽 다 갈림 |
| 마일스톤 | 6/8 vs 6/8 | 4/8 vs 4/8 | M23 **적용**을 만든다(의도대로) |

⚠️ **경계 축은 이 격자에서 M20·M21 을 갈라내지 못했다.** 그래도 **뺀다면 그것도 사후
조정**이므로 그대로 두고 **결과에 이 사실을 함께 싣는다.**

⚠️ **이 확인은 룰 전용 계획(`rule_only_plan`)으로 한 것이다.** 실제 M33 실행은 LLM 계획을
쓰므로 세션 길이가 달라질 수 있고, 그러면 변별력도 달라진다.

⚠️ **활동창-hard 8건은 룰 전용 계획에서 전부 미배치**라 M21 이 arm 과 무관하게 실패한다
(**바닥 효과**). 다만 **재분해가 더 짧은 세션을 만들면 통과할 수 있으므로** 원리적으로
막힌 것은 아니다 — ③층 클램프 범위가 `[15분, 120분]` 이다. 실제로 그렇게 되는지가
M33 이 답할 것 중 하나다.

### 3.4 분리 보고 — 섞지 않는다

```
M33(일반 34건)      과   M33(challenge 16건)   을 따로 낸다
M26-core(일반)       과  M26-core(challenge)   〃
```

⚠️ **둘을 합쳐 단일 성과 수치를 만들지 않는다.** 난이도가 다른 표본을 섞으면 그 비율은
"우리가 고른 난이도 배합" 을 재는 것이 된다.

## 4. 무엇을 보고하는가

**M26-core 와 M18 을 항상 나란히 낸다** (§5 등록). M18 은 AND 에 없고, 연속량이라 arm 별
**분포**로 싣는다 — ④층이 분량을 어느 쪽으로 밀었는지가 그 자체로 결과다.

| | A(없음) | B(상세) | C(빈 피드백) |
|---|---|---|---|
| M26-core | | | |
| M18a·M18b 중앙·미달수 | | | |
| M30 (반려된 케이스 중 수리) | — | | |
| M31 (지적과 무관한 값 변경) | — | | |

**일반 34건 / challenge 16건 두 벌.**

### 4.1 페어링 — 같은 분모여야 한다

어떤 케이스가 한 arm 에서만 N/A 가 되면 **ΔM26-core 가 서로 다른 케이스 집합의 차**가
된다. **세 arm 모두에서 M26-core 가 정의된 케이스만** ΔM26-core 의 분모에 넣고, 빠진
케이스 수를 함께 적는다.

### 4.2 M33 의 신뢰구간 — **산출법을 지금 고정한다**

*"하한 CI > 0"* 만 적으면 나중에 방법을 고를 여지가 남는다.

> **케이스 단위 페어드 부트스트랩** — 케이스를 **복원 추출**로 리샘플하고(케이스가 표집
> 단위다), 각 리샘플에서 ΔM26-core = M26-core(B) − M26-core(A) 를 다시 계산한다.
> **10,000회**, **양측 95%** 백분위 구간. 난수 시드 **42** 를 코드에 고정한다.

⚠️ **행(계획)이 아니라 케이스를 리샘플한다.** 같은 케이스의 세 arm·3회 반복은 상관이
있어, 행 단위로 재면 구간이 **거짓으로 좁아진다**(L1-7A §4 에서 같은 실수를 했다).

⚠️ **페어드다.** A 와 B 를 독립 표본으로 보면 케이스 간 난이도 차이가 분산에 들어간다.
같은 케이스의 (A, B) 쌍을 함께 리샘플한다.

⚠️ **일반 34건과 challenge 16건에 각각 따로** 적용한다. 섞어서 한 구간을 만들지 않는다.

### 4.3 반복

케이스당 **3회**, 1차 추정은 **`PRIMARY_REPEAT = 0`** 의 고유 케이스. 반복을 독립 표본으로
세지 않는다(L1-7B 가 M29 에 쓰는 규칙과 같다).

## 5. 사전 고정한 해석 규칙

| 결과 | 결론 |
|---|---|
| **M33 > 0** 이고 신뢰구간 하한 > 0 | ④층 유지 |
| **M33 ≤ 0** | *"검토기 프롬프트를 더 다듬자"* 가 **아니라** **"이 층을 룰로 대체하거나 걷어내자"** 를 설계 안건으로 올린다 |
| **M34 ≈ 0** | 개선이 **비평 내용이 아니라 재시도**에서 왔다 — 상세 피드백 생성 비용을 재검토한다 |
| M33 의 부호를 결정 못 함 | 천장/바닥 효과나 표본 부족을 먼저 적고, **지표 설계를 다시 본다.** 부호를 억지로 만들지 않는다 |

⚠️ **승인율(`approved` 비율)을 계획 품질 지표로 쓰지 않는다.** 검토기가 자기 판정으로
자기를 채점하는 구조가 된다. 검토기는 **측정 도구가 아니라 측정 대상**이다.

⚠️ **반복 자기개선에서 심판 점수는 오르는데 사람 점수는 정체·하락**했고 원인이 심판과
생성자의 컨텍스트 공유였다는 보고가 있다. **우리 재분해 루프가 정확히 그 구조다** —
승인율 상승을 수렴 증거로 쓰지 않는다.

⚠️ **3번이 가장 어렵다.** M30 은 "그 결함이 더 이상 없는가" 를 판정해야 하는데, v3 는

### 6.1 권고 — M33 을 먼저 내고, **M34 는 별도 실행으로 센다**

M33 은 이 실험의 **1차 지표**이고 v3 로 계산된다. M34 는 v4 배선까지 필요해 리드타임이
길다. **M33 을 먼저 내는 것**이 "④층이 필요한가" 에 더 빨리 답한다.

**M34 는 같은 실험의 후속 측정이 아니라 별도 실행이다.** 검토기가 v3 → v4 로 바뀌면
**반려 판정 자체가 달라져** 재분해 대상 집합이 M33 실행과 같지 않다. 같은 실험이라고
부르면 두 표본을 섞게 된다.

→ **별도 지문·별도 결과 문서**로 내고, M33 결과와 **케이스 단위로 대조하지 않는다.**

⚠️ 그리고 **M33 을 낼 때 M34 를 안 낸 사실을 함께 적는다** — M33 만으로는 이득이
비평에서 왔는지 재시도에서 왔는지 못 가른다.
