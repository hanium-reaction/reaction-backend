# ADR-0007: 마일스톤 층 — 마감까지의 뼈대와 4주 주기의 분리

- 상태: 승인 (2026-08-23)
- 관련: #milestones (Stage A/B), #225 (구간 커버리지), #coverage, Issue #21-A (주간 리뷰),
  #117 (주간 재계획), ADR-0005 §2.5.1 (First Plan 상태머신)
- 구현(예정): `goal_nodes(node_type='milestone')` · `orchestrator/first_plan_milestones.py` ·
  `orchestrator/first_plan_adapter.py` · `api/routes/planning.py` · `api/routes/review.py`

## 배경

계획 지평은 **한 번에 최대 4주**다(`first_plan_adapter._MAX_PLAN_WEEKS`). 분해 LLM 이
20s 안에 만들 수 있는 양의 한계이자, 그보다 먼 구간은 어차피 수정될 거라 정밀도가 가짜라는
판단이다. 그 주석은 이렇게 적혀 있다 — "제품이 주간 리포트·재계획과 월간 리포트로 계획을
계속 다듬는다."

그 전제가 성립하지 않는다. 세 가지가 확인됐다.

**① 사용자가 확정한 마일스톤이 조용히 사라진다.** Stage A 에서 3~5개를 확인받고
`goal_decompose` 프롬프트가 "추가·삭제·병합·개명 금지"로 묶지만, `shape_action_plan` 이
`items[:max_sessions]` 로 자르고 `_prune_to_leaves` 가 leaf 없는 branch 를 버린다. 재현
(마감 4주·주 3회·마일스톤 5개×4세션): 20세션 → 12세션, branch 는 `['MS1','MS2','MS3']` —
**MS4·MS5 가 경고 없이 소멸**했다. 이 레포가 다른 모든 축소(대기 단계 제거·회차 보충·
하루 상한 초과·케이던스 미달)에 대해 지키는 "조용히 줄이지 않는다"가 여기서만 깨진다.

**② 4주 이후를 만드는 코드가 없다.** `replan` 은 **룰 only, LLM 0회**이고 후보는
"미래 미착수 블록이 달린 액션"과 "활성 블록 없는 `planned` 백로그"뿐이다. 즉 기존
`action_item` 을 **뒤로 미는** 것만 한다. 새 내용을 만드는 경로가 없어서, 4주치를 소비하면
회복 수락분 말고는 내놓을 게 없다. 그런데 `horizon_coverage_notice` 는 사용자에게
"매주 재계획이 이어받는다"고 말하고 있다.

**③ 마일스톤이 주기를 넘어 살아남지 못한다.** 승인마다 `_archive_goal_nodes` 가
`tree_kind='plan'` 트리를 **전량** 보관하고 새로 INSERT 한다. 마일스톤은 매번 새 행이라
진척이 누적될 수 없다.

셋은 같은 뿌리다: **마감까지의 뼈대를 들고 있는 층이 없다.** 4주 캡이 정당하려면 그
너머를 아는 층이 있어야 한다.

## 1. 세 층으로 나눈다

```
Goal            마감까지 (몇 달)          기존
 └ Milestone    마감까지 전 구간을 덮음    ← 신설. 주기를 넘어 살아남는다
    └ Leaf      현재 4주 창만              기존 계획 트리. 주기마다 교체
```

비용 구조가 이 모양을 지지한다. 마일스톤 층은 **3~5개 · LLM 1콜로 전 구간**을 덮고,
비싼 leaf 분해(12~20개)는 **가까운 4주만** 한다. 지금은 두 층이 같은 4주에 갇혀 있어
4주를 넘는 목표는 뒤가 통째로 없다.

## 2. 마일스톤 ≠ 주기 (커서 모델)

**1 마일스톤 = 1 주기로 묶지 않는다.**

- **4주**는 *시간* 제약이다 (LLM 20s · 먼 미래의 가짜 정밀도).
- **마일스톤**은 *의미* 단위다. "React 기초 문법"은 1주, "배포까지"는 6주일 수 있다.

묶으면 마일스톤 개수가 `마감까지 주 수 ÷ 4` 로 정해져 "한눈에 방향이 보이게 굵직하게
3~5개"라는 취지가 사라진다.

```
마일스톤:  [MS1        ][MS2  ][MS3      ][MS4              ]   마감까지 전 구간
주기:      [ 4주 ][ 4주 ][ 4주 ][ 4주 ][ 4주 ]...              시간 창이 그 위를 흐른다
            ↑ 커서
```

한 주기가 큰 마일스톤의 **일부만** 덮을 수도, 작은 마일스톤 **여럿을** 덮을 수도 있다.
전환은 "4주가 지나면 다음 마일스톤"이 아니라 **"이번 주기 세션이 떨어지면 커서 지점부터
다음 4주치"** 다. MS1 이 안 끝났으면 MS1 의 뒷부분을 이어서 분해한다.

구조 자체는 이미 이렇다 — `total_sessions = 주당 × horizon_weeks(≤4)` 로 분량을 먼저
정하고 프롬프트가 "앞쪽 마일스톤부터 순서대로 세션화하라"고 시킨다. 바꿀 것은 **잘린 뒷
마일스톤이 사라지는 것**과 **다음 주기가 이어받을 방법이 없는 것** 둘이다.

## 3. 진척도는 저장하지 않고 파생한다

`action_items` 가 `goal_node_id` 와 `status` 를 이미 들고 있다. 마일스톤 진척 = 그 아래
leaf 들의 status 롤업이다. 재승인으로 leaf 가 보관돼도 `goal_node_id` 는 계보로 남으므로
(`_archive_goal_nodes` 규약) 주기가 쌓이면 이력이 자동 누적된다.

두 벌 두지 않는 이유:

- `action_item.status` 가 이미 진실 소스이고, AGENTS §1.4 가 그것을 회복 결정으로
  바꾸지 못하게 잠가 뒀다. 복사본을 두면 그 잠금이 무의미해진다.
- 같은 판정을 여러 곳이 따로 조립하면 **갈린다** — 인터뷰 명료성 지표가 정확히 그렇게
  샜다(api-change-log v1.70).
- 4계층 메모리 규약(`memory/README.md`): 라이터는 자기 레이어만 쓴다. 진척도는
  Raw Execution / Derived Stats 의 것이지 Planning 레이어가 복사해 둘 값이 아니다.

**예외 — 마일스톤 완료 판정은 저장한다** (`goal_nodes.completed_at`, 컬럼 이미 존재).
롤업만으로는 "세션은 다 했는데 아직 아니다"와 "세션은 안 했지만 다른 경로로 달성했다"를
표현할 수 없고, 그 판단은 AI 가 아니라 사용자 몫이다.

## 4. 두 개의 리뷰 — 단위가 다르다

| | 단위 | 경계 | 목적 | 저장 |
|---|---|---|---|---|
| 주간 리뷰 (기존, S21) | 사용자 | 달력 주(월~일) | 이번 주 KPI | `period_summaries` `weekly` |
| **주기 리뷰** (신설) | **목표** | 그 목표의 주기 경계 | **다음 주기 분해의 근거** | **없음 — 파생** |
| 사용자 월간 리뷰 (후속) | 사용자 | **달력 월** | 이번 달 전반 | `period_summaries` `monthly` |

**주기 리뷰를 `period_summaries` 에 넣지 않는다.** 그 표는 `goal_id` 컬럼이 없고 유니크
키가 `(user_id, period_type, start_date)` 라, 같은 날 시작한 목표 둘이 서로를 덮어쓴다.
목표 단위 요약이 들어갈 자리가 아니다.

**그리고 저장할 새 사실이 없다.** §3 에 따라 주기 리뷰는 `goal_nodes` + `action_items`
위의 계산된 뷰다. 저장하지 않으면 부수적으로 **'월간'이라는 달력 의미가 붙지 않는다** —
주기는 목표별 시작일 기준 4주라, 달력 월로 끊으면 말일 근처에 만든 계획이 며칠 만에
"다음 주기" 를 보게 된다.

"근거가 흔들리면 안 된다"는 요구는 이미 충족된다: **다음 주기 Draft 의 `payload` 에 그
시점의 근거가 프리즈된다**(First Plan draft 가 `outcome` 스냅샷을 담는 것과 같은 방식).
승인된 draft 가 곧 "이 근거로 이 계획을 세웠다"는 기록이다.

주간 리뷰가 `period_summaries` 에 쓰는 것도 진실 소스라서가 아니라 **캐시**다 — 없으면
`_from_kpi` 로 즉석 계산해 내려준다(`routes/review.py`). 주기 리뷰도 같은 패턴으로 가고,
느려지면 그때 캐시를 붙인다.

## 5. 전환 제안 판정 — 날짜가 아니라 잔여 세션

"마지막 주"를 **마지막 블록 날짜**로 판정하면 무너진다: 배치가 대부분 실패해 블록이 몇 개
없으면 승인 직후가 마지막 주가 되고, 아직 아무것도 안 한 사용자에게 다음 달을 열어준다.

판정은 **"다음 주에 할 게 남았는가"** 다. 재계획이 후보를 고를 때 이미 보는 데이터
(미래 미착수 블록)를 그대로 쓴다. 가드 셋을 모두 통과할 때만 제안한다:

| 조건 | 아니면 |
|---|---|
| 다음 주 이후 미착수 세션이 없다 | 아직 마지막 주 아님 — 제안 없음 |
| 이번 주기에 종결된 세션이 하나라도 있다 (`done`/`failed`) | 시작도 안 함 → 주간 재계획으로 |
| 열린 마일스톤이 남아 있다 | 없음 → **목표 완료 확인** |

첫 조건이 *4주 경과*와 *마일스톤 조기 완료*를 **둘 다** 잡는다 — 트리거를 따로 만들지
않는다. 마일스톤을 일찍 끝내면 세션도 일찍 떨어져 전환이 자연히 앞당겨진다.

## 6. 전환 생성은 `replan` 에 넣지 않는다

재계획의 안전성은 "LLM 0회 · 기존 goal/node/action 재사용 · 중복 0"이라는 보증에서
나온다. 여기에 생성을 섞으면 그 보증이 깨진다. 사용자에게도 *이번 주 밀린 것 미루기*와
*다음 한 달을 새로 여는 것*은 무게가 다른 사건이라 확인 카드를 따로 받는 게 정직하다.

전환 생성은 별도 Draft + 승인(HITL)으로 간다 — First Plan 과 같은 패턴이다.

## 7. 제안은 알림이 아니라 화면

AGENTS §1.4 잠금: 알림은 3 클래스만(`morning_brief`/`pre_card`/`evening_reflection`),
주 ≤ 3건. **주기 전환용 4번째 클래스는 만들지 않는다.**

제안은 주간 리뷰(S21) 응답의 목표별 섹션에 실린다 — 마지막 주에만 그 섹션이 "다음 한 달
열기"로 바뀐다. 새 화면도 새 크론도 필요 없다: `run_weekly_review_for_user` 는 이미
`generate_replan` 앞에서 돌고 있고(`routes/planning.py`), 일요일 03:00 precompute 도 있다.

## 8. 주기 리뷰도 룰 only

주간 리뷰가 LLM 0회인 이유(집계는 룰의 일, 한 줄 평은 P2)가 그대로 적용된다. 마일스톤
진척 롤업도 산수다. **LLM 은 다음 주기 leaf 분해 한 곳에만** 쓴다 — 그래야 "제안은 공짜,
생성은 사용자가 수락할 때만"이 되어 토큰이 사용자 수에 비례하지 않는다.

## 9. 마이그레이션 없이 간다 — 이미 파둔 빈 슬롯 셋

| 슬롯 | 상태 | 이 ADR 에서 |
|---|---|---|
| `goal_nodes.node_type = 'milestone'` | enum 에 있고 **아무도 안 씀** (`_NODE_TYPE_MAP` 은 branch→subgoal) | 마일스톤 층 |
| `goals.status = 'completed'` | enum 에 있고 **아무도 안 씀** | 목표 완료 |
| `period_summaries.period_type = 'monthly'` | enum 에 있고 **아무도 안 씀** | 사용자 월간 리뷰(후속) |

`goal_nodes` 는 만다라 작업(`1ee508b967ba`)이 `completed_at`·`locked`·`source` 를 이미
넣어 뒀고 `order_index`·`depth`·`archived_at` 은 원래 있다 — 마일스톤에 필요한 컬럼이
그대로 갖춰져 있다. **전 구간 새 테이블 0 · 마이그레이션 0** 으로 간다. 새 컬럼이
필요해지면 그때 AGENTS §8(합의) 절차를 밟는다.

## 10. 마일스톤 정체성은 서버가 발급한다

재생성·다음 주기에서 "같은 마일스톤"을 제목으로 매칭하면 취약하다(LLM 이 개명하거나
사용자가 고친다). Stage A 응답에 서버가 id 를 실어 보내고 FE 가 왕복시켜 승인 때 실
UUID 로 확정한다. 이후 generate 는 제목이 아니라 `milestoneNodeId` 를 참조한다.

`goal_nodes.locked` 를 그대로 재사용해 **사용자가 직접 고친 마일스톤은 재생성이 건드리지
못하게** 한다 — 만다라 `regenerate-branch` 와 같은 규칙이다.

## 11. 마일스톤 세팅에 총 가용 시간을 싣는다

`plan_milestones.v1.md` 가 받는 변수는 제목·카테고리·why_now·현재수준·완료기준·접근·
자료·**마감**까지고, **주당 가용 시간이 없다**. 그래서 "석 달 안에 주 3시간"인 사용자에게
물리적으로 불가능한 분량의 마일스톤이 나올 수 있고, 그게 뼈대로 고정되면 주기가 아무리
돌아도 끝나지 않는다.

`generate_milestones` 는 이미 `context_from_outcome` 의 `prompt_vars` 를 통째로 넘기므로
`weekly_hours`·`session_length`·`horizon_weeks` 가 도착해 있다. 프롬프트가 쓰지 않을
뿐이다. 총 가용 시간(주당 × 마감까지 주 수)을 실어 "이 안에 실제로 담기는 크기로 끊어라"를
넣는다.

## 12. 마감 없는 목표에는 마일스톤 층이 없다

"끝이 있는 목표냐"의 신호는 **`outcome.horizon`(= `goals.deadlines`) 유무**다. 새 신호를
만들지 않는다 — `_horizon_weeks` 가 이미 "마감 없음 = *짧다*가 아니라 *끝이 없다*"로 읽어
4주 리듬을 굴리고, `extend_action_plan_to_horizon` 도 같은 축을 쓴다.

리듬형(마감 없음)은 마일스톤을 만들지 않고, 주기 전환이 "같은 리듬으로 다음 4주"라
**LLM 0회 룰만으로** 된다. 분해할 새 내용이 없기 때문이다. 비싼 경로는 마일스톤 있는
목표에만 붙는다.

질문을 새로 추가하지 않는다 — 마감을 안 적었어도 끝이 있는 목표면 **마일스톤 확인 카드가
뒤집는 자리**가 된다(어차피 사용자가 뼈대를 확인하는 화면이다).

## 전체 흐름

```
인터뷰 → 마일스톤 3~5개 (마감 + 총 가용 시간 기준, 사용자 확정, goal_nodes 영속)
           ↓
        주기 N: 커서 지점부터 4주치 leaf 분해(LLM 1회) → 승인 → 실행
           ↓  잔여 세션 소진 (4주 경과 또는 마일스톤 조기 완료)
        주기 리뷰(파생·룰): 뭘 했나 · 마일스톤 어디까지 · 왜 밀렸나
           ↓  가드 3개 통과 → 주간 리뷰 화면에서 제안
        주기 N+1: 같은 근거로 다음 4주치 → 승인 → 실행
           ↓  열린 마일스톤 소진
        목표 완료 확인 → goals.status='completed'
```

**2번이 이 설계의 관문이자 유일한 고위험 지점이다.** `_archive_goal_nodes` 가 막고 있던
것은 "재승인 반복 시 트리 무한 누적"이라, 층을 쪼갤 때 그 방어가 유지되는지 실 DB
테스트(`test_plan_supersede_sql.py` 계열)로 확인해야 한다.

> **완료 메모(2026-08-24)**: 2번을 구현하며 이 문서가 열어두지 않았던 구조 결정을
> 두 가지 내렸다.
> 1. **마일스톤은 leaf 분해 트리와 부모-자식으로 얽지 않는다** — `parent_node_id=NULL`,
>    `depth=1`(`subgoal`과 같은 깊이지만 `node_type` 으로 구분, `tree_kind` 로 만다라와
>    나누는 것과 같은 원리). 매 주기 `_archive_goal_nodes` 가 교체하는 core/subgoal/leaf
>    트리에 마일스톤이 걸려 있으면 그 트리가 archive 될 때 같이 끌려간다.
> 2. **LLM 분해가 만든 branch 에서 역추적하지 않고, 사용자가 확인·편집한 원본
>    `MilestoneDraft` 를 그대로 영속한다.** 분해는 세션 수 상한에 잘리거나 마일스톤을
>    통째로 스킵할 수 있어(1번 PR 이 고지하는 바로 그 함정), LLM 출력에서 역산하면
>    확정한 마일스톤 자체가 조용히 사라질 수 있다. `POST /plans/generate` 의 확정
>    목록을 `plan_drafts.payload` 에 실어 승인 때 그대로 읽는다(`_persist_milestones_if_new`,
>    한 번만 만들고 이미 있으면 조용히 무시).
>
> **§11(프롬프트에 총 가용 시간 싣기)은 이번에 안 했다** — 순수 LLM 프롬프트 튜닝이라
> 영속화와 분리 가능하고, 이번 PR 은 고위험 지점(archive 층 분리) 하나에만 집중했다.

## 열어둔 것

- **주기 이력의 저장** — "지난 달엔 이만큼 했다"를 보여주려면 주기 *경계* 자체가 필요한데
  그것만은 파생이 애매하다(재승인·블록 편집으로 흔들린다). 1차는 현재 주기만 계산한다.
  보관된 leaf 가 `goal_node_id` 를 물고 남아 과거 재구성은 어차피 가능하다.
- **사용자 월간 리뷰**(`period_type='monthly'`) — 표가 이미 맞으므로 독립 후속.
- **마일스톤이 여러 목표에 걸칠 때** — 한 계획은 heaviest 목표 하나만 다루므로(현행 계약)
  범위 밖. 다중 목표 동시 계획을 열 때 다시 본다.
